**[Maven alpha `0.1.0-alpha.1` is released](https://github.com/yuri4n/h34s/releases/tag/v0.1.0-alpha.1)** with eleven private `dev.yuri4n` libraries, including native, ZIO, Kyo, and optional Schema/NuxtHub modules. The [successful release workflow](https://github.com/yuri4n/h34s/actions/runs/38779659501) verified authenticated registry consumers. The [release guide](https://github.com/yuri4n/h34s/blob/main/docs/releases.md) lists coordinates and authentication.

The shared CLI and Nuxt module are published as [`@yuri4n/h34s-nuxt@0.1.0-alpha.1`](https://github.com/yuri4n/h34s/releases/tag/npm-v0.1.0-alpha.1). The npm workflow verifies the authenticated registry archive and an isolated offline consumer. Nuxt 4.3.1 passes packed-package HTTP checks in CI; Nuxt 4.4.2 passes the same checks locally on Linux x86_64 with Node 24.19.0. See [npm tooling](/guide/npm-tooling) for installation and application configuration. There is no project generator yet.

Choose the modules your application needs. Define its models, services, dependency provisioning, database resources, and route mounts yourself; the guides show how. The runnable demo lives in `examples/nuxt/`, while `website/` contains this documentation site. Neither application is required to consume h34s.

## ZIO integration

| Capability                  | Current scope                                                                        |
| --------------------------- | ------------------------------------------------------------------------------------ |
| `ZHandler.define`           | Request-scoped ZIO execution with native-value conversion                            |
| Application services        | Provide your layers with ordinary ZIO operations; an `AppHandler` helper is optional |
| Error responses             | Approved safe messages; opaque unexpected failures outside development               |
| Development diagnostics     | Enable the npm Nuxt module to connect cause and trace details to development mode    |
| Source maps                 | Node reads Scala.js maps directly; retained helper supports Nitro composition        |
| Streaming                   | Pull-driven adapter for direct Node HTTP, with cancellation and scoped cleanup       |
| Optional PostgreSQL example | App-defined Skunk insert/read, validation, and one connection per request            |
| Optional schema reader      | Model-owned decoding, transformation, and validation through separate modules        |

The [guides](/guide/getting-started) show how to configure these paths using the demo source. `AppHandler`, database configuration, and service layers are example application code.

## Kyo integration

The native Kyo integration and its application example are included in the same repository. Follow the [Kyo guide](/guide/kyo) for `KHandler.define`, `Env` composition, and request cleanup.

| Capability                  | Current scope                                                                    |
| --------------------------- | -------------------------------------------------------------------------------- |
| `KHandler.define`           | Kyo execution, request context, native values, and request `Scope`               |
| Application services        | Provide your services with `Env.run`; the demo defines an `AppHandler` helper    |
| Request decoding            | NativeConverter-only models and `KHandler.readBody[A]`                           |
| Errors and development mode | Explicit safe failures, opaque production errors, and the Nuxt development flag  |
| Cancellation                | Node response close interrupts request work and awaits scope cleanup             |
| Runnable example            | Database-free GET/POST greeting routes with independent Scala.js output          |
| Development loading         | Direct Node loading of linked modules, with a Nitro worker restart after linking |
| Development source maps     | Node reads adjacent Scala.js maps through the `pnpm dev` script                  |

The pre-release prepared-checkout validation passed 17 Kyo tests, including three real HTTP tests for JSON request/response conversion, converter defects in production/development, and client-abort cleanup. All 31 existing ZIO tests also passed with the shared linker update, and both examples compiled and linked under Java 25. Thirteen development-tool checks covered module loading and source maps. Live Nuxt GET/POST smoke checks passed for native Kyo models and service provisioning while ZIO `/api/test` returned `abc`. Plain `pnpm dev` mapped a Kyo exception to `Greetings.scala`, and a real Scala edit/relink refreshed the HTTP response without manually restarting Nuxt. Those historical checks cover the prepared checkout. The published alpha has separate authenticated Maven consumer evidence in the release workflow linked above.

The configured demo loads both linked Scala.js modules directly in development and watches their output directories for worker reloads. Its `package.json` pins `h3` 1.15.4 as a direct Node runtime dependency. The earlier bundled ZIO setup supplied the composed-map evidence below; the map-composition helper remains available.

This slice does not add Kyo streaming, Schema, Skunk integration, or a ZIO-to-Kyo runtime bridge. Kyo RC7 logs and swallows `Scope.ensure` finalizer failures; callers must not rely on those failures changing an HTTP response. See the [Kyo lifecycle guidance](/guide/kyo#keep-resource-ownership-explicit).

## ZIO validation performed

The earlier ZIO development profile exercised:

- 31 Scala handler and stream tests, including conversion, error boundaries, provisioning, and cleanup.
- Six source-map checks and application development linking.
- Nuxt startup and direct HTTP streaming.
- A real PostgreSQL 16 insert/read using SCRAM authentication.
- Safe 422 responses for blank, null, missing, and incorrectly typed input.
- A real query failure returning development diagnostics with a Scala source frame.
- Connection cleanup after successful requests, input failures, and query failure.

Production error suppression and Nitro's production replacement of the development flag were checked separately. Those checks do not establish a complete production application build or deployment.

The library's response-close tests use real h3 with mocked Node responses. An actual client-abort integration check remains to be added. Interactive breakpoint stepping is also unverified, although source-map stack remapping and source inclusion have been checked.

The release workflow runs API and application tests, production-links both examples, validates POMs, and builds independent ZIO/Kyo consumers from a disposable Maven repository. After a matching tag publishes packages, it repeats the consumer checks against the private registry before creating a GitHub prerelease. That workflow passed for the published alpha. Its evidence is separate from the historical development results above.

Binary and source jars are configured for publication. Scaladoc jars are omitted for this alpha because Scala 3.5's documentation generator fails while reading generated inline h3 facades. The guides and source jars remain available; fixing Scaladoc is follow-up work.

## Limits to account for now

- **Application adoption:** release checks cover independent Maven/h3 consumers and a packed npm module in a minimal external Nuxt application. Complete application templates and fresh-machine setup still need dedicated validation.
- **Streaming:** the scoped adapter supports direct Node HTTP. Nitro's no-socket local-fetch path is rejected, and other deployment adapters need their own lifecycle checks.
- **Buffering:** one upstream chunk is pulled at a time, but h3 does not await Node response `drain`. There is no established end-to-end HTTP memory bound.
- **Database lifetime:** the example opens one connection per request. It does not provide an application-wide pool, transaction guide, or migration system.
- **Production output:** `pnpm build` clears stale output and production-links both application modules into their mounted directories before Nuxt. Deployable packaging, Nix, and platform-specific lifecycle checks remain separate work.
- **Type generation:** `scala:types` compiles the native module and runs ScalablyTyped's TypeScript-to-Scala facade generation. Scala-to-TypeScript wire generation is not wired up.

## Planned work

The agreed direction includes these separate implementation slices:

1. Extend optional schema/codec support beyond the integrated ZIO Schema bridge; Kyo Schema and additional JSON/YAML codecs need separate validation.
2. Extend npm tooling compatibility with additional independently tested consumer profiles.
3. Automate route discovery, mounting, and TypeScript wire-type generation.
4. Extend the Kyo integration with streaming and optional Schema/database adapters, preserving cancellation and resource ownership.
5. Add an optional example of application-scoped Skunk pooling with explicit startup, shutdown, and request/stream leases.
6. Validate deployable Nuxt packaging and add the planned Nix and sbt-native-packager paths.
7. Investigate compiler-derived type information, symbol navigation, and editable examples for documentation.

The current documentation presents static source examples. It does not provide semantic Scala hovers, an editable compiler, or a browser-hosted Nitro/PostgreSQL playground. Those features require separate tooling and validation.

See [architecture](/reference/architecture) for the boundaries behind this roadmap and [adoption](/guide/adoption) for the three intended ways to use h34s.
