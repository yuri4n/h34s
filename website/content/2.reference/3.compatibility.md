A compatibility profile is a combination that we test together. It should
connect dependency versions, a pinned toolchain, an OS/architecture target,
and reproducible checks. Installing a package successfully does not by
itself establish compatibility.

The greeting application uses built-in English/root locale formatting without currency metadata. It excludes Kyo’s full currency database at the application level to keep generated development output smaller; the reusable library retains upstream locale support. See [locale data](/guide/kyo#choose-application-locale-data).

The Kyo version, Scala compiler, and build JDK are selected together. RC7's compiler macros require Java 25 class files, even when the target is Scala.js. Use JDK 25 to run sbt for this profile. The separately verified ZIO-only profile above uses JDK 21; production remains Node in both cases.

Development loads linked Scala.js modules directly through Node, with imports limited to the configured output directories. Nitro watches those directories and reloads its worker after linking. The `pnpm dev` script enables Node source maps for the adjacent Scala.js map files. This profile uses the direct `h3` runtime pin above to resolve the linked modules' package imports.

Evidence from the prepared Linux x86_64 checkout: 17 Kyo boundary and HTTP tests pass, including a real client abort that awaits cleanup; all 31 ZIO regression tests pass with the updated linker under both Java 21 and Java 25. Both examples compile and development-link under Java 25. Thirteen development-tool checks pass: seven module-loading checks and six source-map checks. Live Nuxt GET/POST Kyo requests pass alongside ZIO `/api/test`. A real Scala edit/relink refreshed the HTTP response without manually restarting Nuxt, and plain `pnpm dev` mapped a Kyo exception to the original `Greetings.scala` source. Resolved classpaths contain no ZIO in Kyo and no Kyo in ZIO. These historical checks did not include the new release-consumer workflow or Nix validation.

Do not assume that replacing the Kyo artifact with another release, or compiling it with the ZIO example's older compiler, is supported. This profile does not yet cover Kyo Schema, streaming, or database adapters. Native h3 bindings remain independent of both effect runtimes.

## Connect each profile to Nix

The planned Nix experience should make a tested profile directly usable:

1. Pin Node, pnpm, Java, sbt, and build dependencies with a committed Nix
   lock. Link the matrix row to that exact lock revision.
2. Provide a development shell for that profile and document the matching
   sbt/pnpm commands for people who do not use Nix.
3. Run the same application pipeline: production Scala.js linking and
   required generation, then Nuxt/Nitro, then application packaging.
4. Validate clean, sandboxed builds and the resulting Node application.
   Exercise HTTP responses, streams/cancellation, and Skunk operations.
5. Record the actual host targets and CI evidence. NixOS, another Linux
   distribution, and macOS need their own validation where offered.

A working development shell establishes tool availability. Production
reproducibility also needs dependency pinning, sandboxed builds, and
checks against the packaged application. Runtime database credentials
and mutable data must stay outside the Nix store and packaged outputs.

No Nix commands are presented here as working setup instructions yet.
The intended relationship is one tested build profile, one pinned
toolchain, and one application build pipeline shared by Nix and ordinary
sbt/pnpm users.

## Extend the matrix with evidence

Add a row when its exact versions and targets are known. Promote it to a
supported release profile only after CI validates compilation, handler
behavior, its optional integrations, and the documented consumer setup.
Include links to those runs and the relevant Nix lock revision. Keep
untested combinations and planned adapters explicitly separate.

Schema support remains optional throughout: NativeConverter-only users
must not acquire a mandatory ZIO Schema or Kyo Schema dependency.
