One runtime does the hard work. The h3 transport, request lifecycle, cancellation, streaming, error rendering, configuration access and application-scoped resources are implemented once, in Kyo. The ZIO API is a hand-written adapter over that core. Your application adds only the modules it needs.

> **Status.** This describes `0.2.0-alpha.1`. The older `0.1.0-alpha.1` had two independent runtimes; see the [migration guide](/reference/migration).

## Layers

| Layer            | Module                                                               | What it gives you                                                                                                                                                                                                                                  |
| ---------------- | -------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Native layer     | `h3-ext`                                                             | Pure values shared by every runtime: `EventHandler`, `Request`, `ResponseHead`, `Status`, `SetCookie`, `HandlerOptions`, `SafeError`, `HttpError`, `InvalidInput`, `ConfigError`, `Secret`. Internal h3, Node and Nitro facades. No effect library |
| Kyo core         | `kyo-h3-ext`                                                         | `KHandler.define`, request lifecycle, body limits, `Response`, error rendering, diagnostics, `RuntimeConfig`, `Shared`, streams                                                                                                                    |
| ZIO adapter      | `zio-h3-ext`                                                         | `ZHandler.define`, `Response` over `ZState`, `ZStream` bodies, `ZRuntimeConfig`, `ZShared`, and the bridge that waits for ZIO finalizers                                                                                                           |
| Schema bridges   | `native-converter-kyo-schema-ext`, `native-converter-zio-schema-ext` | `derives Schema, NativeSchema`                                                                                                                                                                                                                     |
| ZIO converters   | `native-converter-zio-ext`, `native-converter-zio-json-ext`          | `NonEmptyList` and zio-json `Json` converters                                                                                                                                                                                                      |
| Storage          | `kyo-nuxthub-ext`, `zio-nuxthub-ext`                                 | `KHubKv.mount`, `ZHubKv.mount` over Nitro storage                                                                                                                                                                                                  |
| npm tooling      | `@yuri4n/h34s-nuxt`                                                  | Build CLI, route collection and registration, typed declarations, Nuxt module, development loading, source maps, Nitro plugin                                                                                                                      |
| Your application | your code                                                            | Models, services, `AppHandler`, resources, routes, database, deployment                                                                                                                                                                            |

```text
h3-ext                                 (no effect library)
├── kyo-h3-ext                         (Kyo core)
│   ├── kyo-nuxthub-ext
│   └── zio-h3-ext                     (also uses native-converter-zio-ext, kyo-zio, ZIO)
│       └── zio-nuxthub-ext            (also uses kyo-nuxthub-ext)
├── native-converter-kyo-schema-ext    (also uses kyo-schema)
├── native-converter-zio-schema-ext    (also uses zio-schema)
└── native-converter-zio-ext           (also uses ZIO)
    └── native-converter-zio-json-ext
```

Dependencies point one way. Kyo modules never depend on ZIO; ZIO modules get Kyo through the adapter.

## Follow one request

1. Nitro routes the request to a linked Scala.js module. The Nuxt module registered it for the route your handler declares with `.at(Route...)`, from the manifest that `h34s-scala` wrote after linking.
2. The h34s Nitro plugin has attached a frozen record: development and debug flags, runtime config, storage.
3. `KHandler.define` takes one `Request` snapshot and runs your function on its own fiber, in a request `Scope`, with an empty `Var[ResponseHead]`.
4. Your program reads the body, calls services, sets the head with `Response.*`, and returns the body.
5. After the program and its finalizers finish, the core writes the head and body once, with the success or [failure rule](/guide/kyo#fail-safely) and your `HandlerOptions`.
6. If the client disconnected, the core interrupts the program, waits for cleanup, and writes nothing.

`ZHandler.define` runs your ZIO program in one ZIO fiber per request, with a `ZState[ResponseHead]` and a ZIO `Scope`, then hands the result and the head to the core.

## Where your code goes

| Layer          | Lives there                                                                           | Owner        |
| -------------- | ------------------------------------------------------------------------------------- | ------------ |
| Business logic | Services and programs, Kyo `A < S` or ZIO                                             | You          |
| Interfaces     | Your traits and the h34s values                                                       | You and h34s |
| Implementation | The h34s runtime and your service implementations                                     | h34s and you |
| Application    | Your `AppHandler`: configuration, then `Shared`/`ZShared`, then `Env`/`ZLayer` wiring | You          |

`AppHandler` is the demo's name for this wiring point. It is your code, not an h34s export.

## Errors

<!-- claude 2026-10-19: changed: finalizer failures behave the same in both runtimes (issue #40) -->

A handler is an error boundary. Only a `SafeError` you fail with through the typed channel reaches the client; everything else is an opaque 500 with diagnostics only in development or debug mode. A failing finalizer is logged and keeps the response, in Kyo and in ZIO.

## Not included

- TypeScript types guessed from Scala classes: generated types describe what each converter writes, and other converters give `unknown`.
- Database clients, pools and migrations: use [kyo-sql or Skunk](/guide/database) directly.
- Packaging and deployment: Nix and sbt-native-packager are planned.
- Non-Node Nitro presets: not tested.
