h34s is a toolbox for running Scala.js in your Nuxt/Nitro application. Choose independently consumable native h3 bindings, ZIO handlers, or Kyo handlers, then add optional adapters and build tooling as needed. Both effect APIs run on their own runtime; your application defines and provides its services.

## Module responsibilities

| Boundary           | Responsibility                                                                   |
| ------------------ | -------------------------------------------------------------------------------- |
| Native h3 bindings | Scala.js facades and transport contracts, without a mandatory ZIO or Kyo runtime |
| ZIO integration    | ZIO handlers, request context, scopes, streams, and ZIO runtime execution        |
| Kyo integration    | Native Kyo handlers, request scopes, errors, and Kyo runtime execution           |
| Application        | Models, configuration, services, resource ownership, and route mounts            |
| npm tooling        | Build CLI, Nuxt development loading, source maps, and diagnostics plugin         |

The [Maven alpha release](https://github.com/yuri4n/h34s/releases/tag/v0.1.0-alpha.1) publishes eleven reusable artifacts under `dev.yuri4n` version `0.1.0-alpha.1`. The separate [npm release](https://github.com/yuri4n/h34s/releases/tag/npm-v0.1.0-alpha.1) publishes build orchestration and Nuxt development integration as `@yuri4n/h34s-nuxt@0.1.0-alpha.1`; see [npm tooling](/guide/npm-tooling) for setup. sbt owns Scala dependencies and linking settings, while the npm CLI invokes those tasks before Nuxt.

## Follow a request

Create a Nuxt route file to mount your Scala.js export, and provide your services before passing the program to `ZHandler.define`. For shared provisioning, define a helper in your application; the Notes example calls it `AppHandler`. Nuxt routes requests to the mounted export, and `ZHandler.define` supplies `SH3Event` and scopes execution.

The endpoint then reads request data and calls those services. Its result is converted through `NativeConverter` into a JavaScript value for h3. The boundary handles effect execution and approved error responses.

```scala
val listNotes = AppHandler.define:
    ZIO.serviceWithZIO[Notes](_.list)
```

Define `AppHandler` and `Notes` in your application; neither is an h34s export. To reproduce the Notes example, compose database configuration, a scoped Skunk connection, and `NotesLive` using the [handler guide](/guide/handlers). For your own application, provide the services your endpoints need. You can also provide them directly when calling `ZHandler.define`, without creating a helper.

The Kyo example follows the same division of responsibility. Its `AppHandler` uses `Env.run` to provide `Greetings`, then calls `KHandler.define`. Kyo's boundary supplies `KH3Event` and resolves `Async`, `Scope`, and `Abort[Throwable]`. The [Kyo guide](/guide/kyo) includes the application source.

## Assign resource ownership explicitly

A `ZLayer` describes construction. Reusing its value does not automatically share the constructed resource across requests. A `ZEnvironment` holds services but does not itself define their cleanup lifetime.

The current Notes application opens one connection per request. Its request scope owns that connection and releases it when execution completes or fails. Supported HTTP streaming keeps the request alive while h3 consumes the source and scoped cleanup completes.

For an application-wide database pool, define startup and shutdown ownership plus scoped request leases in your app. The example does not yet implement or validate this pattern. See [database](/guide/database) and [streaming](/guide/streaming) for current behavior.

In Kyo, `Env.run` provides a service but does not own its resources. The request `Scope` owns request finalizers. The first Kyo example uses an immutable service with no database resource. Kyo streaming and database adapters remain planned. Kyo RC7 also logs and swallows failures from `Scope.ensure` finalizers; its cleanup-error semantics differ from ZIO's.

## Keep effect runtimes independent

ZIO programs execute with ZIO; Kyo programs execute with Kyo. `kyoH3Ext` and `kyoExample` depend on the native bindings and Kyo, independently of the ZIO modules. The ZIO example also remains independent of Kyo. The Nuxt demo in `examples/nuxt/` mounts exports from both examples to demonstrate their independent APIs. Choose either API in your own app; installing one does not require the other.

The integrations share native transport contracts and test the same response and error expectations through their own runtimes. They do not translate arbitrary ZIO programs into Kyo. Any shared runtime implementation would need explicit interoperability, cancellation, and resource-lifetime validation before adoption.

## Keep conversions at the boundary

The current API uses `NativeConverter` for Scala/native-value conversion. It avoids JSON string round trips solely to move values between Scala and JavaScript. HTTP wire serialization remains a separate concern.

Converters do not automatically establish request validation or TypeScript wire types. Both handler APIs work with NativeConverter alone. The optional ZIO Schema integration is included in separate modules; Kyo Schema remains planned. See [decoding choices](/guide/handlers#choose-your-decoding-approach). Future generated TypeScript must describe the actual wire representation, including custom converters.

## Build and runtime

Configure your Scala.js build to emit ES modules, list their output directories in the npm tooling config, and create Nuxt route files that import the handler exports. Nitro runs those handlers in Node. The demo links into `examples/nuxt/server/.scala` and `examples/nuxt/server/.scala-kyo` and includes handwritten mounts in `examples/nuxt/server/api`. h34s does not discover or mount routes automatically.

Java and sbt are build-time dependencies. If your app uses PostgreSQL, run it as an external service and configure its connections in application code.

The repository's `pnpm build` command builds the demo through one pipeline: clear previous Scala output, production-link both applications, verify their output, then build Nuxt/Nitro. A failed link stops the build. Planned generation, Nix, and sbt-native-packager support should extend that pipeline rather than maintain a competing implementation.

The release workflow checks production linking and library consumers. Full deployment, Nix reproducibility, and application packaging require separate validation. The development workflow is documented in [getting started](/guide/getting-started); [status](/reference/status) separates implemented behavior from upcoming work.

| `examples/nuxt/server/plugins`                   | Application-specific Skunk Node integration                         |

| `website/`                                       | Separate documentation application                                  |

The aggregate also contains recovered experiments, including migration helpers. Their presence does not make them a required persistence layer or a supported public API.
