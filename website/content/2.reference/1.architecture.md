h34s keeps native h3 bindings and effect integrations in one repository, with independently consumable modules and an idiomatic API for each effect system. ZIO is the primary documented experience; the first-class [Kyo API](/guide/kyo) provides its own native handler boundary and application example.

## Module responsibilities

| Boundary           | Responsibility                                                                   |
| ------------------ | -------------------------------------------------------------------------------- |
| Native h3 bindings | Scala.js facades and transport contracts, without a mandatory ZIO or Kyo runtime |
| ZIO integration    | ZIO handlers, request context, scopes, streams, and ZIO runtime execution        |
| Kyo integration    | Native Kyo handlers, request scopes, errors, and Kyo runtime execution           |
| Application        | Models, configuration, services, resource policy, and `AppHandler`               |
| Nuxt integration   | Mount linked Scala.js exports as Nitro routes                                    |

The [Maven alpha release](https://github.com/yuri4n/h34s/releases/tag/v0.1.0-alpha.1) publishes eleven reusable artifacts under `dev.yuri4n` version `0.1.0-alpha.1`. The separate [npm tooling](/guide/npm-tooling) packages build orchestration and Nuxt development integration; its first publication is pending. sbt owns Scala dependencies and linking settings, while the npm CLI invokes those tasks before Nuxt.

## Follow a request

Nuxt routes a request to a mounted Scala.js export. `ZHandler.define` supplies `SH3Event` and scopes the program's execution. The application's `AppHandler` provides its services with ordinary ZIO layers.

The endpoint then reads request data and calls those services. Its result is converted through `NativeConverter` into a JavaScript value for h3. The boundary handles effect execution and approved error responses.

```scala
val listNotes = AppHandler.define:
    ZIO.serviceWithZIO[Notes](_.list)
```

`AppHandler` belongs to the application. The example supplies database configuration, a scoped Skunk connection, and `NotesLive`; another application can supply different services. See [handlers](/guide/handlers) for the full composition.

The Kyo example follows the same division of responsibility. Its `AppHandler` uses `Env.run` to provide `Greetings`, then calls `KHandler.define`. Kyo's boundary supplies `KH3Event` and resolves `Async`, `Scope`, and `Abort[Throwable]`. The [Kyo guide](/guide/kyo) includes the application source.

## Assign resource ownership explicitly

A `ZLayer` describes construction. Reusing its value does not automatically share the constructed resource across requests. A `ZEnvironment` holds services but does not itself define their cleanup lifetime.

The current Notes application opens one connection per request. Its request scope owns that connection and releases it when execution completes or fails. Supported HTTP streaming keeps the request alive while h3 consumes the source and scoped cleanup completes.

An application-wide database pool would need startup and shutdown ownership plus scoped request leases. That is a later integration, with its own lifecycle tests. See [database](/guide/database) and [streaming](/guide/streaming) for current behavior.

In Kyo, `Env.run` provides a service but does not own its resources. The request `Scope` owns request finalizers. The first Kyo example uses an immutable service with no database resource. Kyo streaming and database adapters remain planned. Kyo RC7 also logs and swallows failures from `Scope.ensure` finalizers; its cleanup-error semantics differ from ZIO's.

## Keep effect runtimes independent

ZIO programs execute with ZIO; Kyo programs execute with Kyo. `kyoH3Ext` and `kyoExample` depend on the native bindings and Kyo, independently of the ZIO modules. The ZIO example also remains independent of Kyo. The root Nuxt application can mount exports from both examples.

The integrations share native transport contracts and test the same response and error expectations through their own runtimes. They do not translate arbitrary ZIO programs into Kyo. Any shared runtime implementation would need explicit interoperability, cancellation, and resource-lifetime validation before adoption.

## Keep conversions at the boundary

The current API uses `NativeConverter` for Scala/native-value conversion. It avoids JSON string round trips solely to move values between Scala and JavaScript. HTTP wire serialization remains a separate concern.

Converters do not automatically establish request validation or TypeScript wire types. Both handler APIs work with NativeConverter alone. The optional ZIO Schema integration is included in separate modules; Kyo Schema remains planned. See [decoding choices](/guide/handlers#choose-your-decoding-approach). Future generated TypeScript must describe the actual wire representation, including custom converters.

## Build and runtime

Scala.js linking emits ZIO application ES modules to `server/.scala` and Kyo modules to `server/.scala-kyo`. Nuxt mounts them and Nitro runs them in Node. Java and sbt are build-time dependencies, and PostgreSQL is an external service.

`pnpm build` runs one application pipeline: clear previous Scala output, production-link both applications, verify their output, then build Nuxt/Nitro. A failed link stops the build. Planned generation, Nix, and sbt-native-packager support should extend that pipeline rather than maintain a competing implementation.

The release workflow checks production linking and library consumers. Full deployment, Nix reproducibility, and application packaging require separate validation. The development workflow is documented in [getting started](/guide/getting-started); [status](/reference/status) separates implemented behavior from upcoming work.

## Source locations

| Path                                             | What to inspect                                                   |
| ------------------------------------------------ | ----------------------------------------------------------------- |
| `scala-modules/exts/h3`                          | Native bindings                                                   |
| `scala-modules/exts/zio-h3`                      | Handler boundary, stream adapter, behavior tests                  |
| `scala-modules/exts/native-converter-zio`        | ZIO native-conversion integration                                 |
| `scala-modules/exts/kyo-h3`                      | Kyo handler boundary and tests                                    |
| `scala-modules/exts/native-converter-zio-schema` | Optional schema/native conversion                                 |
| `scala-modules/exts/zio-h3-schema`               | Optional schema-based ZIO request reader                          |
| `scala-modules/svr`                              | Application models, services, configuration, handlers, and schema |
| `scala-modules/kyo-example`                      | Kyo models, services, and `AppHandler`                            |
| `server/api`                                     | Current export mounts                                             |
| `server/plugins`                                 | Application-specific Skunk Node integration                         |
| `packages/nuxt`                                  | Shared CLI, Nuxt module, diagnostics plugin, and source-map helpers |
| `h34s.config.mjs`                                | Application output modules and expected linked entry files         |

The aggregate also contains recovered experiments, including migration helpers. Their presence does not make them a required persistence layer or a supported public API.
