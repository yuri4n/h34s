Enable the [npm Nuxt module](/guide/npm-tooling) in your app to connect Scala handler diagnostics to Nuxt development mode. Once enabled, it installs the shared development integration; endpoint code needs no separate debug flag. To try the configured repository example, use the [development commands](/guide/getting-started).

The [Kyo slice](/guide/kyo) uses the same server-owned development flag. Its unexpected failures include exception causes and stack details in `debug.cause`. The example below shows the ZIO diagnostic payload.

## Inspect a development failure

An unexpected failure returns HTTP 500. In development, its response includes the original ZIO cause and trace:

```json
{
  "errors": ["Internal server error"],
  "debug": {
    "cause": "...original exception, nested causes, and ZIO trace..."
  }
}
```

Read `debug.cause` in the browser Network panel or the failed fetch response. The server also logs the cause. Safe errors and explicit `ZHandler.failWith` responses retain their approved status and payload.

When you enable the Nuxt module, it installs a runtime plugin equivalent to:

```ts
export default defineNitroPlugin((nitroApp) => {
  nitroApp.hooks.hook('request', (event) => {
    event.context.h34s = { development: import.meta.dev }
  })
})
```

Use the module's plugin directly; you do not need to copy it into your app. Nitro replaces `import.meta.dev` with `false` in production. The library accepts only boolean `true` and defaults to opaque errors if the plugin is absent. Request headers and query parameters cannot enable diagnostics.

Development causes can contain database and configuration details. Use the development server with trusted access. Production error responses omit `debug`; full diagnostics remain in server logs.

## Follow a stack frame into Scala

Configure your Scala.js output directories in [the npm tooling config](/guide/npm-tooling#describe-the-application-outputs) and enable source maps in your build. In the repository example, this setup loads linked Scala.js modules directly in Node:

1. Scala.js links the applications into `examples/nuxt/server/.scala/*.js` and `examples/nuxt/server/.scala-kyo/*.js`, with adjacent `.js.map` files.
2. The npm module's development loader keeps the outputs from `h34s.config.mjs` external to Nitro's development bundle. Node reads their Scala.js maps directly.

The packaged source-map helper also supports map composition when Nitro transforms a Scala.js module. It supplies the incoming Scala.js map so the resulting Nitro map can reach the original source.

The loader normalizes local file URLs and embeds project Scala source content. Dependency URLs remain in the map, but the loader does not download remote source files. Some dependency source views may therefore be unavailable.

The example's `build.sbt` explicitly enables source maps for `fastLinkJS`. Enable them in your own Scala.js build too. The Nuxt module enables map composition and source content in development, leaving production source-map settings untouched.

The example's `pnpm dev` script enables Node source-map support; add `--enable-source-maps` to your own development command too. For a custom Node entry point, use:

```sh
node --enable-source-maps <entry.mjs>
```

Replace `<entry.mjs>` with that entry point. This option maps stack positions; ZIO's trace additionally identifies effect boundaries that a JavaScript call stack may no longer retain.

## Attach a Node debugger

Start Nuxt with its inspector option from the repository root:

```sh
pnpm dev --inspect
```

Attach a Node debugger using the inspector address printed by Nuxt. Server handlers execute in Node, so use that inspector session rather than the browser page's JavaScript context.

Look for the original Scala file in Sources. Source maps provide original locations; local source files or embedded content provide the source view. They do not supply Scala expression evaluation, JVM-style collection inspection, or a full Scala debugger. Interactive breakpoint stepping has not yet been verified.

## Rebuild after editing

Run `pnpm run scala:fast` after a Scala edit, or keep `pnpm run scala:watch` running. Both commands read the configured application modules through the packaged CLI. Nitro watches the linked JavaScript and maps and replaces its worker after a change. Wait for linking and worker restart before inspecting another failure.

If the location looks stale, first confirm that linking completed and the generated files changed. Edited source cannot reliably describe an older linked bundle.

## Checks and evidence

```sh
node --test scripts/scala-source-maps.test.mjs
sbt 'zioH3Ext/test' 'nuxtsvr/fastLinkJS'
```

The source-map checks cover local sources, source roots, remote sources, and development-only integration. Handler tests cover development causes, opaque responses outside development, safe errors, and cleanup defects.

The earlier bundled setup verified a composed Scala.js → esbuild → Rollup map through Node stack remapping. A real query failure in that Nuxt example returned a frame mapped to `notes/Notes.scala:23`, and the final Nitro map included project Scala source content. The current direct-module setup separately mapped a Kyo exception to `Greetings.scala` and refreshed a live response after a Scala edit/relink.

These checks establish source-location mapping, not a completed production build or interactive debugger workflow. The current [validation status](/reference/status) keeps those limits explicit.
