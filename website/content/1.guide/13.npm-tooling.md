`@yuri4n/h34s-nuxt` packages the build CLI, route collection and registration, development loading, source maps and the h34s Nitro plugin. You configure your Scala build, models and services; the package links Scala.js, mounts your Scala routes and connects them to Nuxt.

**[`@yuri4n/h34s-nuxt@0.1.0-alpha.1` is published](https://github.com/yuri4n/h34s/releases/tag/npm-v0.1.0-alpha.1)** in the private GitHub npm registry.

> **Use the package version that matches your Scala libraries.** This source builds the package as `0.2.0-alpha.1`, like the Scala libraries, with its own release tag, `npm-v0.2.0-alpha.1`. Check that release before installing from the registry. The Kyo core reads runtime config, storage and the close hook from the package's new Nitro plugin. The published `0.1.0-alpha.1` package supplies only the development flag, so with it `RuntimeConfig` and `KHubKv.mount` fail with `ConfigError("h34s Nitro plugin is not installed")`.

## Install

Configure the private registry in `.npmrc`, with the token from your environment:

```ini
@yuri4n:registry=https://npm.pkg.github.com
//npm.pkg.github.com/:_authToken=${GITHUB_PACKAGES_TOKEN}
```

Use a classic PAT with `read:packages` and commit only the placeholder. In GitHub Actions, save it as `PACKAGES_READ_TOKEN` and map it to `GITHUB_PACKAGES_TOKEN`.

Install the package with the version of your Scala libraries, and h3:

```sh
pnpm add -D @yuri4n/h34s-nuxt@0.2.0-alpha.1
pnpm add h3@1.15.4
```

With the published `0.1.0-alpha.1` Scala libraries, use `pnpm add -D @yuri4n/h34s-nuxt@0.1.0-alpha.1` instead. To review the source instead, run `npm pack ./packages/nuxt --pack-destination /tmp` in an h34s checkout and install the tarball in a disposable consumer.

## Describe the outputs

Create `h34s.config.mjs` beside `package.json`:

```js
import { defineConfig } from '@yuri4n/h34s-nuxt/build'

export default defineConfig({
  modules: [
    {
      project: 'server',
      output: 'server/.scala',
    },
  ],
})
```

`project` is the sbt project ID. `output` is the generated directory, which a production build clears. `entries` is optional: list the linked files you mount with your own route files, and the CLI checks them. Without it, an output must contain at least one h34s handler. Configure `fastLinkJS` and `fullLinkJS` in `build.sbt` to write ES modules there; see [adoption paths](/guide/adoption#configure-the-scalajs-module).

## Enable the module

```ts
export default defineNuxtConfig({
  modules: ['@yuri4n/h34s-nuxt'],
})
```

The module mounts the routes of each output's `h34s-routes.json` as lazy Nitro handlers, watches the outputs, installs development loading and source maps, and registers the Nitro plugin. The plugin hands your Scala handlers a record that requests cannot change:

| Entry                  | Used by                                                                    |
| ---------------------- | -------------------------------------------------------------------------- |
| `development`, `debug` | [Diagnostics](/guide/debugging)                                            |
| `runtimeConfig`        | `RuntimeConfig` / `ZRuntimeConfig` ([configuration](/guide/configuration)) |
| `storage(base)`        | `KHubKv.mount` / `ZHubKv.mount` ([storage](/guide/storage))                |
| `onClose`              | `Shared` / `ZShared` release ([lifetimes](/guide/lifetimes))               |

The module also declares `runtimeConfig.h34s.debug`, so `NUXT_H34S_DEBUG=true` can turn on diagnostics. Keep it off in production. Remove any copied development plugin, and any `runtime/development.mjs` entry you added to `nitro.plugins` yourself.

## Run one pipeline

```json
{
  "scripts": {
    "scala:fast": "h34s-scala dev",
    "scala:watch": "h34s-scala watch",
    "scala:full": "h34s-scala build",
    "dev": "node --enable-source-maps node_modules/nuxt/bin/nuxt.mjs dev",
    "dev:scala": "pnpm run scala:fast && pnpm run dev",
    "build": "pnpm run scala:full && nuxt build"
  }
}
```

Run `pnpm dev:scala` to link and start Nuxt, and keep `pnpm scala:watch` running while you edit. After each link, the CLI loads the linked modules in a separate Node process and writes the route manifest and one `.d.ts` declaration per handler module; see [routes and typed $fetch](/guide/routes). `pnpm build` clears old output, production-links, checks every entry, writes the manifests and declarations, and only then builds Nuxt; a failed link stops it. Large linked outputs make Nitro's bundling memory-hungry: the demo, with a Kyo and a ZIO application, needed `NODE_OPTIONS=--max-old-space-size=8192` for `nuxt build`. The CLI accepts `--root` and `--config`; the module accepts `{ configFile }`.

Declare routes in Scala with `.at(Route...)`. A one-line route file (`export { default } from '../.scala/notes-get.js'`) still works when you prefer Nuxt's file layout for a route.

The package adds nothing to your Scala classpath. It needs Node 22.18 or later; the published `0.1.0-alpha.1` passed packed-package HTTP checks with Nuxt 4.3.1 in CI and Nuxt 4.4.2 locally. Windows and Nix need separate validation; see [compatibility](/reference/compatibility).
