Your Scala handlers declare their own routes. h34s mounts them in Nitro and types their responses, so you write no route file in `server/api` and no TypeScript interface for the `{ data }` and `{ errors }` bodies.

## Mount a handler

Export the handler as the `default` export of its own Scala.js module, and give it a route with `.at`:

```scala
@JSExportTopLevel("default", "notes-get")
val listNotes: EventHandler = AppHandler.define(NotesHandler.list).at(Route.get("/api/notes"))
```

With a braceless handler function, put `.at` on its own line:

```scala
@JSExportTopLevel("default", "kyo-greeting-post")
val personalizedGreeting: EventHandler = AppHandler
  .define: request =>
      for
        input    <- request.body.json[GreetingRequest]
        greeting <- Env.use[Greetings](_.greet(input.name))
      yield greeting
  .at(Route.post("/api/kyo/greeting"))
```

Then link with `h34s-scala dev` and start Nuxt. The link step prints the routes it found.

| Route value                                                            | Matches             |
| ---------------------------------------------------------------------- | ------------------- |
| `Route.get(path)`, `post`, `put`, `patch`, `delete`, `head`, `options` | One method          |
| `Route(Method.Patch, path)`                                            | The method you pass |
| `Route.any(path)`                                                      | Every method        |

Paths use Nitro's syntax: `/api/notes`, a parameter in `/api/notes/:id`, and a last segment `**` for the rest of the path. An invalid path fails when the module loads, so the link step reports it. The ZIO API is the same, with `Route` from `dev.yuri4n.exts.zioh3`. One linked module mounts one route.

## What h34s does

After linking, `h34s-scala build`, `dev` and `watch` load your linked modules in a separate Node process and read each default export's route and response types. They write into each output directory:

- `h34s-routes.json`: the module, route and method of each handler;
- `<module>.d.ts` next to each handler module, with the real response body.

The Nuxt module registers each route with Nitro as a lazy handler, so `routeRules` apply as usual. In development, a changed list of routes reloads Nitro's routes without a restart. Loading runs your modules' top-level code: keep top-level handler values free of side effects, and acquire resources in `Shared` or `ZShared`.

## Call routes with typed $fetch

```ts
const { data } = await $fetch('/api/notes')
// data: { id: number; text: string }[]
```

The type includes the `HandlerOptions` envelope: `{ data: T }` by default, `T` with `SuccessEnvelope.Raw`. A `Unit` body has no content; a stream is `string`. Nitro does not type errors, so each declaration exports `ErrorBody`:

```ts
import type { ErrorBody } from '~~/server/.scala/notes-post'

await $fetch('/api/notes', {
  method: 'POST',
  body: { text: '' },
  onResponseError({ response }) {
    const body: ErrorBody = response._data
    // body.errors: { message: string; path?: string }[]
  },
})
```

## Where the types come from

The type describes what your converter writes, never a guess from the Scala class:

- `NativeSchema` types (Kyo Schema or ZIO Schema) give their fields and wire names; see [schemas](/guide/schema#typescript-types). The Kyo bridge checks its type against its encoder with sample values.
- native-converter's built-in converters give theirs. `Long` is a string, because native-converter writes it as text.
- Any other converter gives `unknown`. Mix `WireType.Described` into your own converter to type it, and check it in a test with `wireType.describes(value)`.

## Use a route file instead

The one-line route file still works, and the declaration next to the linked module types it too:

```ts
// server/api/notes.get.ts
export { default } from '../.scala/notes-get.js'
```

Leave `.at` off that handler: a route file and `.at` for the same route register it twice. List `entries` in `h34s.config.mjs` for outputs that have only route-file handlers.

## Troubleshooting

- **404:** run `h34s-scala dev` and check that it prints the route. If Nuxt warns that `h34s-routes.json` is missing, link first and restart Nuxt.
- **`Two Scala.js handlers mount ...`:** two exports share a route and method.
- **`... has no h34s handlers`:** export a handler from `KHandler.define` or `ZHandler.define`, or list `entries`.
- **A response is `unknown`:** derive `NativeSchema`, or mix in `WireType.Described`.

Nitro types response bodies only: request bodies and query strings have no generated type.
