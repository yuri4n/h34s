h34s is an unpublished development slice for writing Nuxt/Nitro handlers in Scala.js. The current example uses ZIO. Start with its database-free stream route, then add the [Notes database example](/guide/database).

This guide runs the application at the repository root. The `website/` directory contains this documentation site; run the commands below from the repository root.

## Prerequisites

The development example has been exercised with this toolchain:

| Tool    | Version |
| ------- | ------- |
| Node.js | 24      |
| pnpm    | 10.34.4 |
| Java    | 21      |
| sbt     | 1.11.7  |

Java and sbt build the Scala.js output. Node runs it inside Nitro. Docker with Compose is only needed for the local PostgreSQL example.

The repository pins sbt in `project/build.properties` and supplies JVM memory settings in `.jvmopts`. This is the example's validated toolchain, not a compatibility matrix for released packages.

## Install and link

Clone `yuri4n/h34s` using your existing GitHub access. The repository is private. There is no published package or project generator yet.

```sh
git clone https://github.com/yuri4n/h34s.git
cd h34s
pnpm install --frozen-lockfile
sbt 'nuxtsvr/fastLinkJS'
```

Scala.js writes the development modules to `server/.scala`. The existing files in `server/api` mount their exports as Nitro handlers.

Start Nuxt after linking finishes:

```sh
NODE_OPTIONS=--max-old-space-size=8192 pnpm dev
```

The unoptimized example currently needs an 8 GB Node heap during Nitro bundling. Allow enough machine memory for that process and sbt's 4 GB heap, or finish linking before starting Nuxt.

## Make the first request

Wait for Nitro to finish building. In another terminal, use the address printed by Nuxt:

```sh
curl --fail http://127.0.0.1:3000/api/test
```

The response body is `abc`. No database configuration is required for this route.

The endpoint in `scala-modules/svr/src/main/scala/dev/yuri4n/svr/handlers/TestHandler.scala` is:

```scala
import dev.yuri4n.exts.zioh3.ZHandler
import zio.stream.ZStream

import scala.scalajs.js.annotation.JSExportTopLevel

@JSExportTopLevel("default", "test")
val handler = ZHandler.define:
    ZHandler.sendStream(ZStream("a", "b", "c"))
```

`ZHandler.define` supplies the request context and scope, runs the effect, and handles the JavaScript boundary. See [streaming](/guide/streaming) for lifecycle behavior and current transport limits.

## Edit and repeat

After a Scala change, run `sbt 'nuxtsvr/fastLinkJS'` again. Nuxt watches the linked JavaScript. For continuous Scala linking, keep this task running in another terminal:

```sh
sbt '~nuxtsvr/fastLinkJS'
```

Wait for both Scala linking and Nitro rebuilding before checking a change. If a response still reflects old code, confirm that linking finished successfully.

Nuxt development mode enables detailed Scala error responses and source maps. Follow [debugging](/guide/debugging) to inspect causes or attach a Node debugger.

## Check the implementation

These checks do not require PostgreSQL:

```sh
sbt 'zioH3Ext/test' 'nuxtsvr/fastLinkJS'
node --test scripts/scala-source-maps.test.mjs
```

The full HTTP smoke check also writes a note to a running development database. Run it after completing the [database guide](/guide/database).

## Prepared cloud environment

In the prepared checkout, activate its tools first:

```sh
cd /workspace/h34s
source /workspace/tooling/activate.sh
/workspace/tooling/h34s-sbt 'nuxtsvr/fastLinkJS'
```

Use `/workspace/tooling/h34s-sbt` in place of `sbt` there. It is a Java launcher; omit shell-launcher flags such as `-batch`. The cloud setup also has an ignored `.nuxtrc` selecting Node's native SQLite connector for Nuxt Content and disabling remote font providers.

The development workflow has been exercised in that prepared environment. A fresh-machine setup without its local adjustments remains to be validated. See [status](/reference/status) for the exact boundary of the current work.
