h34s provides ZIO and Kyo APIs for writing Nuxt/Nitro handlers in Scala.js. The repository includes examples for both APIs. Start with the ZIO database-free stream route, then add the [Notes database example](/guide/database).

The [Kyo API](/guide/kyo) has its own database-free example and linking output. It runs Kyo programs on Kyo's runtime.

This guide runs the application at the repository root. The `website/` directory contains this documentation site; run the commands below from the repository root.

## Prerequisites

Use this toolchain for the combined application:

| Tool    | Version |
| ------- | ------- |
| Node.js | 24      |
| pnpm    | 10.34.4 |
| Java    | 25      |
| sbt     | 1.11.7  |

Java and sbt build the Scala.js output. Node runs it inside Nitro. Docker with Compose is only needed for the local PostgreSQL example.

The repository pins sbt in `project/build.properties` and supplies JVM memory settings in `.jvmopts`. Native and ZIO modules use Scala 3.5.2; Kyo modules use Scala 3.9.0. Both use Scala.js 1.22.0. See [compatibility](/reference/compatibility) for historical checks and the configured alpha profile.

## Install library artifacts

The private Maven libraries are published under `dev.yuri4n` version `0.1.0-alpha.1`, with authenticated consumer checks in the [release workflow](https://github.com/yuri4n/h34s/actions/runs/38779659501). The [release installation guide](https://github.com/yuri4n/h34s/blob/v0.1.0-alpha.1/docs/releases.md) includes registry authentication and a complete Scala.js build. After configuring that resolver, choose one API:

```scala
// ZIO application, Scala 3.5.2
libraryDependencies += "dev.yuri4n" %%% "zio-h3-ext" % "0.1.0-alpha.1"

// Kyo application, Scala 3.9.0 and Java 25
libraryDependencies += "dev.yuri4n" %%% "kyo-h3-ext" % "0.1.0-alpha.1"
```

Install `h3@1.15.4` as a runtime dependency in the Nuxt app. Optional ZIO Schema request decoding comes from `zio-h3-schema-ext`; plain NativeConverter handlers do not need it. The separate [npm build tooling](/guide/npm-tooling) packages the CLI and Nuxt development integration; its npm publication is pending. The repository example below consumes that package locally. There is no project-generator command yet.

## Install and link

Clone `yuri4n/h34s` using your existing GitHub access. The repository is private.

```sh
git clone https://github.com/yuri4n/h34s.git
cd h34s
pnpm install --frozen-lockfile
pnpm run scala:fast
```

`h34s-scala dev` reads both application modules from `h34s.config.mjs` and invokes sbt. Scala.js writes the development modules to `server/.scala` and `server/.scala-kyo`. The existing files in `server/api` mount their exports as Nitro handlers.

Start Nuxt after linking finishes:

```sh
pnpm dev
```

Node loads the linked Scala.js modules directly during development. Nitro watches their output directories and replaces its worker after relinking. This setup enables source maps without the earlier bundling workflow's 8 GB Node heap override. sbt uses the memory settings in `.jvmopts`.

## Make the first request

Wait for Nitro to finish building. In another terminal, use the address printed by Nuxt:

```sh
curl --fail http://127.0.0.1:3000/api/test
```

The response body is `abc`. No database configuration is required for this route.

The endpoint in `scala-modules/svr/src/main/scala/dev/yuri4n/svr/handlers/TestHandler.scala` is:

```scala
import dev.yuri4n.exts.zioh3.ZHandler
import zio.stream.ZStream

import scala.scalajs.js.annotation.JSExportTopLevel

@JSExportTopLevel("default", "test")
val handler = ZHandler.define:
    ZHandler.sendStream(ZStream("a", "b", "c"))
```

`ZHandler.define` supplies the request context and scope, runs the effect, and handles the JavaScript boundary. See [streaming](/guide/streaming) for lifecycle behavior and current transport limits.

## Edit and repeat

After a Scala change, relink its application module. For continuous linking of both examples, keep this task running in another terminal:

```sh
pnpm run scala:watch
```

Wait for both Scala linking and Nitro rebuilding before checking a change. If a response still reflects old code, confirm that linking finished successfully.

Nuxt development mode enables detailed Scala error responses and source maps. Follow [debugging](/guide/debugging) to inspect causes or attach a Node debugger.

## Check the implementation

These checks do not require PostgreSQL:

```sh
sbt 'zioH3Ext/test' 'kyoH3Ext/test' 'nativeConverterZIOSchemaExt/test' 'zioH3SchemaExt/test' 'nuxtsvr/test'
node --test scripts/*.test.mjs packages/nuxt/test/*.test.mjs
```

The full HTTP smoke check also writes a note to a running development database. Run it after completing the [database guide](/guide/database).

For production, `pnpm build` first clears prior linked output and runs `fullLinkJS` for both applications, then builds Nuxt. A failed link stops the build. This pipeline does not establish Nix or deployable application packaging support; see [status](/reference/status).

## Prepared cloud environment

In the prepared checkout, activate its tools first:

```sh
cd /workspace/h34s
source /workspace/tooling/activate-kyo.sh
/workspace/tooling/h34s-pnpm run scala:fast
```

The activation script puts the prepared `sbt` launcher on `PATH` for the npm CLI. `/workspace/tooling/h34s-sbt` also accepts direct Scala commands. The cloud setup also has an ignored `.nuxtrc` selecting Node's native SQLite connector for Nuxt Content and disabling remote font providers.

The development workflow has been exercised in that prepared environment. A fresh-machine setup without its local adjustments remains to be validated. See [status](/reference/status) for the exact boundary of the current work.
