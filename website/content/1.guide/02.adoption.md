h34s is a toolbox, not a framework. You add a Scala.js server module to your Nuxt application, write handlers in Kyo (or ZIO), and mount them as routes. Your models, services, configuration and resources stay yours.

Choose your starting point, then follow [write, mount and run a handler](#write-mount-and-run-a-handler).

## Get the libraries

> **Status.** The API on this site is `0.2.0-SNAPSHOT` on the `feat/kyo-core` branch and is not published yet. Until the next release, publish the branch locally (`sbt releasePublishLocal` with JDK 25, then depend on `0.2.0-SNAPSHOT`) or reference the h34s source projects. The local publish path has not been exercised by hand on this branch. After a release, follow the [release installation guide](https://github.com/yuri4n/h34s/blob/main/docs/releases.md).

Pick modules for your runtime. A Kyo application never needs ZIO. A ZIO application gets Kyo through the ZIO adapter.

| You want | Kyo | ZIO |
| --- | --- | --- |
| Handlers | `kyo-h3-ext` | `zio-h3-ext` |
| Schemas (optional) | `native-converter-kyo-schema-ext` | `native-converter-zio-schema-ext` + `zio-schema-derivation` 1.7.5 |
| Nitro storage (optional) | `kyo-nuxthub-ext` | `zio-nuxthub-ext` |

On the npm side, add `@yuri4n/h34s-nuxt` as a dev dependency and `h3@1.15.4` as a runtime dependency. See [npm tooling](/guide/npm-tooling).

Build with JDK 25, sbt 1.11.7, Scala 3.9.0 and Scala.js 1.22.0. Run with Node 24. See [compatibility](/reference/compatibility).

## Start a new project

1. Create a Nuxt 4 app with Nuxt's own tooling. h34s has no generator.
2. Add an sbt build next to it, as in [configure the Scala.js module](#configure-the-scalajs-module).
3. Add the npm package and the Nuxt module.
4. [Write, mount and run a handler](#write-mount-and-run-a-handler).

Want to see it working first? The [getting-started tutorial](/guide/getting-started) runs the repository demo. The demo is a reference, not a template. You do not need to clone the repository to use h34s.

## Add Scala handlers to an existing Nuxt app

Keep your TypeScript routes. Scala routes live next to them, one route file per export.

1. Add an sbt build (for example in `scala-server/`) that links into a generated directory such as `server/.scala`.
2. Add `@yuri4n/h34s-nuxt` and `h3@1.15.4`, and register the module in `nuxt.config.ts`.
3. Move only the routes you want to Scala.
4. Read your existing `runtimeConfig` keys from Scala with `RuntimeConfig` or `ZRuntimeConfig`; see [configuration](/guide/configuration).

h34s wraps values in `{"data": ...}`. If existing clients expect the raw value, pass `HandlerOptions(success = SuccessEnvelope.Raw)` for those routes. `Raw` sends a string as `text/plain; charset=utf-8` and any other value as JSON (`application/json`), unless you set a content type.

## Add Nuxt to an existing Scala.js project

1. Add a dedicated server module with ES-module output. Depend on your existing model and service modules from it.
2. Create the Nuxt app next to your sbt build and point `h34s.config.mjs` at the server module.
3. Write, mount and run a handler.

Only Scala.js-compatible code can run in Nitro, and the modules your handlers use need Scala 3.9.0. If your backend is JVM-only, cross-build what can run on Scala.js, or keep the JVM server and call it over HTTP. JDBC libraries, including Doobie, do not run in Scala.js. For PostgreSQL inside Nitro, use [kyo-sql or Skunk](/guide/database).

## Configure the Scala.js module

```scala
// project/plugins.sbt
addSbtPlugin("org.scala-js" % "sbt-scalajs" % "1.22.0")
```

```scala
// build.sbt
import org.scalajs.linker.interface.{ModuleKind, OutputPatterns}

lazy val server = project.in(file("scala-server"))
  .enablePlugins(ScalaJSPlugin)
  .settings(
    scalaVersion := "3.9.0",
    libraryDependencies += "dev.yuri4n" %%% "kyo-h3-ext" % "0.2.0-SNAPSHOT",
    scalaJSLinkerConfig ~= (_.withModuleKind(ModuleKind.ESModule)
      .withOutputPatterns(OutputPatterns.fromJSFile("%s.js"))),
    Compile / fastLinkJS / scalaJSLinkerConfig ~= (_.withSourceMap(true)),
    Compile / fastLinkJS / scalaJSLinkerOutputDirectory :=
      (LocalRootProject / baseDirectory).value / "server" / ".scala",
    Compile / fullLinkJS / scalaJSLinkerOutputDirectory :=
      (LocalRootProject / baseDirectory).value / "server" / ".scala",
  )
```

Pin `sbt.version=1.11.7` in `project/build.properties`. For ZIO, use `zio-h3-ext` instead of `kyo-h3-ext`. Keep only generated files in `server/.scala`: a production build clears it.

## Write, mount and run a handler

Write a handler and export it as the `default` export of its own module:

```scala
import dev.yuri4n.exts.kyoh3.*
import org.getshaka.nativeconverter.NativeConverter

import scala.scalajs.js.annotation.JSExportTopLevel

final case class Greeting(message: String) derives NativeConverter

@JSExportTopLevel("default", "hello-get")
val hello: EventHandler = KHandler.define(_ => Greeting("Hello from Scala"))
```

Mount it with a one-line route file, `server/api/hello.get.ts`:

```ts
export { default } from '../.scala/hello-get.js'
```

List the module in `h34s.config.mjs`:

```js
import { defineConfig } from '@yuri4n/h34s-nuxt/build'

export default defineConfig({
  modules: [{ project: 'server', output: 'server/.scala', entries: ['hello-get.js'] }],
})
```

Link and start Nuxt with `pnpm dev:scala` (the scripts are in [npm tooling](/guide/npm-tooling)). Then request `/api/hello`. Expected body: `{"data":{"message":"Hello from Scala"}}`.

If you get a 404, check the route file name and the `default` export. If Nitro cannot resolve `h3`, add `h3@1.15.4` to your app. Route files are the one piece of JavaScript you still write; generated route registration is planned.

## What is verified

The repository's consumer check builds fresh sbt projects for Kyo, ZIO, Kyo Schema and ZIO Schema against a temporary Maven repository and serves real h3 requests with them. A complete Nuxt app created from scratch with these steps has not been verified yet.
