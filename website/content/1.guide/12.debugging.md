h34s keeps production errors opaque and shows full diagnostics while you develop. Your handlers need no debug flag: the h34s Nitro plugin decides, and requests can never change its decision. Install the [npm Nuxt module](/guide/npm-tooling) to get the plugin.

## What clients see

An unexpected failure (anything but an approved `SafeError`) answers 500:

```json
{ "errors": [{ "message": "Internal server error" }] }
```

When diagnostics are on, the same entry carries the cause:

```json
{
  "errors": [{
    "message": "Internal server error",
    "debug": { "cause": "java.lang.IllegalStateException: ...\n\tat ..." }
  }]
}
```

Kyo handlers show the exception's class, message, causes and stack. ZIO handlers show ZIO's full `Cause.prettyPrint`, with ZIO traces and Scala source lines. `SafeError` entries never carry `debug`. The server logs every unexpected failure as `Unhandled h34s handler failure`, in every mode.

## When diagnostics are on

| Flag | Comes from | On when |
| --- | --- | --- |
| `development` | Nitro's `import.meta.dev` | `nuxt dev`; production builds compile it to `false` |
| `debug` | `runtimeConfig.h34s.debug`, read once at startup | `NUXT_H34S_DEBUG=true` at runtime, or `runtimeConfig: { h34s: { debug: true } }` in `nuxt.config.ts` |

The Nuxt module declares `runtimeConfig.h34s.debug: false`, which is why the environment variable can override it. A value your config already sets wins. Nuxt's own `debug` option does not turn on h34s debug mode. Restart after a change.

**Keep debug mode off in production.** Diagnostics send exception messages and stack text to anyone who can trigger a failure, and libraries can put connection details or SQL in those messages. If you turned it on by mistake, unset `NUXT_H34S_DEBUG` and restart.

These flags are tested with a stubbed Nitro runtime and fake plugin records. In a production build of the demo, a failure was opaque by default and carried `debug.cause` with `NUXT_H34S_DEBUG=true`; the database password appeared in neither.

## Map JavaScript back to Scala

During `nuxt dev`, Node loads your linked Scala.js modules directly:

1. `fastLinkJS` writes JavaScript and `.js.map` files to the outputs in `h34s.config.mjs`. Enable maps with `Compile / fastLinkJS / scalaJSLinkerConfig ~= (_.withSourceMap(true))`.
2. The module's development loader keeps those outputs out of Nitro's bundle and imports them as files. Nitro restarts its worker after you relink.
3. Start Nuxt with `node --enable-source-maps` (the `dev` script in [npm tooling](/guide/npm-tooling) does). Stack frames then point at Scala files and lines.

## Attach a debugger

```sh
pnpm dev --inspect
```

Attach a Node debugger to the address Nuxt prints and open the Scala file in Sources. Source maps give locations, not Scala expression evaluation. Breakpoint stepping has not been verified.

After a Scala edit, run `pnpm run scala:fast` (or keep `pnpm run scala:watch` running) and wait for the worker restart before the next request.

On this branch (macOS x86_64, Node 24.19.0, Nuxt 4.3.1), `pnpm dev` showed `debug.cause` with Scala frames for a failing route, and a Kyo stack mapped to `RequestLifecycle.scala` and `KHandler.scala`. The packed-module check (`scripts/check-npm-nuxt.mjs`) covered development diagnostics, source maps and a relink reload on a synthetic project. Relinking the real example under `nuxt dev` and breakpoint stepping are not checked.
