`KHandler.define` turns a Kyo program into an h3 handler. It supplies request context, runs the program on Kyo's runtime, owns the request scope, and converts the result with `NativeConverter`. Define your services in your application and provide them through `Env` before calling `KHandler.define`.

The implementation is integrated in the published Maven alpha. It covers ordinary response values, application services, safe errors, and request cleanup. Kyo streaming, Schema, and database adapters remain separate work. Private Maven coordinates are `dev.yuri4n:kyo-h3-ext_sjs1_3:0.1.0-alpha.1`. See the [release guide](https://github.com/yuri4n/h34s/blob/main/docs/releases.md) for installation and authentication.

## Run the example

To use Kyo handlers in your own app, follow [adoption paths](/guide/adoption) and install only the modules you need. The repository example below is an optional reference.

Use the repository example with the [alpha profile](/reference/compatibility#alpha-010-node24). Kyo RC7 requires JDK 25 at build time because its compiler macros use Java 25 class files. Select JDK 25 for sbt before running these commands; the application still runs in Node. From the repository root:

```sh
pnpm install --frozen-lockfile
sbt 'kyoExample/fastLinkJS' 'nuxtsvr/fastLinkJS'
pnpm dev
```

`kyoExample` writes its ES modules and source maps to `examples/nuxt/server/.scala-kyo`. The Nuxt example in `examples/nuxt/` also mounts ZIO routes, so its startup needs both linking tasks. The Kyo library and `kyoExample` do not depend on ZIO. Linking and testing Kyo alone uses `kyoExample/fastLinkJS` and `kyoH3Ext/test`.

After Nuxt starts, request the address it prints:

```sh
curl --fail http://127.0.0.1:3000/api/kyo/greeting
curl --fail http://127.0.0.1:3000/api/kyo/greeting \
  -H 'content-type: application/json' \
  --data '{"name":"Scala"}'
```

The GET returns `{"message":"Hello, Kyo!"}`. The POST returns `{"message":"Hello, Scala!"}`. Neither route needs a database.

For continuous linking, run `sbt '~kyoExample/fastLinkJS'` in a separate terminal. Wait for linking and the Nitro worker restart before repeating a request.

## Load linked code during development

In the repository example, Node loads linked Scala.js ES modules directly from `examples/nuxt/server/.scala-kyo` and `examples/nuxt/server/.scala`. The development integration limits these external imports to the configured output directories. Nitro watches those directories and restarts its worker when linked files change, replacing Node's module cache. This keeps generated Scala.js code out of Nitro's development bundle.

The `pnpm dev` script starts Node with `--enable-source-maps`, so Node reads the adjacent Scala.js maps directly. A diagnostic probe in the running Nuxt application resolved to the original `Greetings.scala` source. The [debugging guide](/guide/debugging) describes the shared Nuxt development flag and retained support for composed maps.

The example pins `h3` 1.15.4 as a direct runtime dependency so Node can resolve it from the linked modules. Keep that dependency when adopting this setup. `pnpm build` now production-links both examples before building Nuxt. Deployable application packaging and Nix remain separate work.

## Choose application locale data

Kyo RC7 includes a full international currency database. Its generated data adds roughly 40 MB to development JavaScript. The greeting application's `kyoExample` project excludes `locales-full-currencies-db_sjs1_3` and uses scala-java-locales' supported built-in English/root formatting fallback, without currency metadata.

This is application build policy. The reusable `kyoH3Ext` module keeps Kyo's upstream dependencies; applications that need international locale or currency data can retain the full database or choose a custom one through scala-java-locales. Unicode request and response values remain supported.

## Keep endpoint code small

Request your application service with `Env.use`. The exports below come from `examples/nuxt/scala/kyo/src/main/scala/dev/yuri4n/kyoexample/Handlers.scala` and use an application-defined `AppHandler`, shown [below](#resolve-services-in-the-application). That name is optional; h34s exports `KHandler`.

```scala
import dev.yuri4n.exts.kyoh3.KHandler
import kyo.*
import scala.scalajs.js.annotation.JSExportTopLevel

@JSExportTopLevel("default", "kyo-greeting-get")
val greeting = AppHandler.define:
    Env.use[Greetings](_.greet("Kyo"))

@JSExportTopLevel("default", "kyo-greeting-post")
val personalizedGreeting = AppHandler.define:
    for
      input <- KHandler.readBody[GreetingRequest]
      greeting <- Env.use[Greetings](_.greet(input.name))
    yield greeting
```

`Env.use[Greetings]` requests an application service. The handler does not create a runtime or perform Promise conversion. Create `server/api/kyo/greeting.get.ts` in your application to mount the linked GET export:

```ts
export { default } from '../../.scala-kyo/kyo-greeting-get.js'
```

Automated route mounting remains planned. The same setup pattern works alongside existing TypeScript routes; see [adoption paths](/guide/adoption).

## Use NativeConverter directly

Define your request and response models and derive `NativeConverter`, as in this example:

```scala
import org.getshaka.nativeconverter.NativeConverter

final case class GreetingRequest(name: String) derives NativeConverter
final case class Greeting(message: String) derives NativeConverter
```

`KHandler.readBody[GreetingRequest]` reads the h3 body and converts the native JavaScript value. Returning `Greeting` converts it back at the handler boundary. No Schema library or JSON string round trip is required for that conversion.

A converter defines a representation; it does not automatically enforce domain constraints. NativeConverter 0.9 accepts missing or null `String` fields. This small greeting example demonstrates conversion and service composition, not a validated account or form model. Keep constraints in your application's model or decoder when using this path.

Kyo Schema integration is planned as an optional module. Installing it must not change the dependencies or defaults of NativeConverter-only users. The [optional ZIO Schema bridge](/guide/handlers#choose-your-decoding-approach) is a separate integration and does not decode Kyo requests today.

## Resolve services in the application

Define your service and its configuration in your application. This example uses immutable configuration:

```scala
import kyo.*

final case class GreetingConfig(prefix: String)

trait Greetings:
    def greet(name: String): Greeting < Sync

object Greetings:
    def live(config: GreetingConfig): Greetings = new Greetings:
        def greet(name: String): Greeting < Sync =
          Sync.defer(Greeting(s"${config.prefix}, $name!"))
```

In Kyo's type syntax, `Greeting < Sync` means a computation producing `Greeting` with the `Sync` effect. If your handler requests `Env[Greetings]`, resolve that requirement before passing the program to `KHandler.define`. For shared setup, write an application helper like this `AppHandler`:

```scala
import dev.yuri4n.exts.h3.CommonEvHandler
import dev.yuri4n.exts.kyoh3.{HandlerEffects, KHandler}
import kyo.*
import org.getshaka.nativeconverter.NativeConverter

object Services:
    private val config = GreetingConfig("Hello")
    val greetings: Greetings = Greetings.live(config)

object AppHandler:
    def define[A: NativeConverter](
        program: => A < (HandlerEffects & Env[Greetings]),
    )(using Frame): CommonEvHandler =
      KHandler.define(Env.run(Services.greetings)(program))
```

Create `Services` and `AppHandler` in your application, for example in `AppHandler.scala`. h34s does not supply these objects. Change the service implementation or configuration there, or provide services directly when calling `KHandler.define`. Endpoint code continues to ask for `Greetings` through `Env`.

`HandlerEffects` names the effects handled by the boundary: `Async & Scope & Abort[Throwable] & Env[KH3Event]`. `KH3Event` carries the h3 request context. Resolve any additional effects your program requires before calling `KHandler.define`. Scala supplies the `Frame` used by Kyo diagnostics at the call site.

## Keep resource ownership explicit

Providing a service with `Env.run` does not acquire a resource, close it, or create a pool. The greeting service is immutable and owns no connection. For services that own resources, define startup/shutdown handling in your application or acquire them inside the request's Kyo `Scope`.

`KHandler.define` waits for request cleanup on normal completion and failure. A closed Node response interrupts active request work and waits for scope cleanup. This applies to the ordinary responses in this slice; it does not establish streaming support.

Kyo 1.0.0-RC7 logs failures from `Scope.ensure` finalizers instead of propagating them to the handler result. Do not rely on a failed finalizer changing a successful HTTP response into an error. Handle a failure that must affect the response before the program returns, and monitor cleanup diagnostics on the server.

The ZIO Skunk example uses ZIO/Cats resource integration. A Kyo Skunk adapter and application-wide pool need their own lifecycle implementation and tests; they are not included here.

## Choose what a client may see

| Failure                                                      | Response                                                   |
| ------------------------------------------------------------ | ---------------------------------------------------------- |
| A typed `Abort` containing the Kyo integration's `SafeError` | Its approved message and status; the default status is 400 |
| `KHandler.failWith(status, message)`                         | The explicit status and message                            |
| Unexpected exception or defect                               | HTTP 500 with `Internal server error` outside development  |

The error body has the same `errors` array used by the ZIO integration. A `Throwable` that has not been explicitly marked safe keeps its details in server diagnostics. Throwing a `SafeError` as a defect does not make that defect an approved response; use Kyo's typed failure channel or `KHandler.failWith`.

The server-owned `event.context.h34s.development` flag controls development details. Enable the [npm Nuxt module](/guide/npm-tooling) to install the plugin that sets it from `import.meta.dev`; query parameters and request headers cannot enable it. Kyo's `debug.cause` contains exception causes and stack details. See [debugging](/guide/debugging) for the plugin and [development loading](#load-linked-code-during-development) for this branch's source-map setup.
