Use Skunk directly inside Scala.js/Nitro when your application needs PostgreSQL. Define your models, database configuration, SQL, service layers, and schema setup in your application. This guide runs the repository's Notes example to demonstrate those choices; h34s does not require or configure a database.

Complete [getting started](/guide/getting-started) first. Run these commands from the repository root with Docker and Compose available.

## Configure the local database

Both Compose and the Nuxt process need the database settings. In Bash, set local development values and enter your own password:

```bash
export MY_APP_DB_HOST=127.0.0.1
export MY_APP_DB_PORT=5432
export MY_APP_DB_USER=h34s
export MY_APP_DB_NAME=h34s
read -rs -p 'Local PostgreSQL password: ' MY_APP_DB_PASSWORD
export MY_APP_DB_PASSWORD
```

Use a free port if 5432 is occupied. Keep all five exported variables available in the shell you use for both Compose and Nuxt.

If you prefer a local environment file, put it in the ignored `examples/nuxt/.env` and add `--env-file examples/nuxt/.env` to each Compose command below. Nuxt development reads that file from the example's application root.

For an existing PostgreSQL volume, use the database, user, and password chosen when it was initialized. Changing the Compose environment values does not update those stored credentials.

Keep the default Compose project name `h34s` to reuse the existing `h34s_postgres_data` volume after the demo's move. If you previously used another project name, set `COMPOSE_PROJECT_NAME` to that name or add `-p <existing-name>` to each Compose command below.

Start PostgreSQL and check readiness:

```sh
docker compose -f examples/nuxt/docker-compose.yml up -d postgres
docker compose -f examples/nuxt/docker-compose.yml exec -T postgres sh -c 'pg_isready -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
```

First-time initialization can take a moment. Repeat the readiness command until it reports `accepting connections` before starting the application.

The example's Compose configuration mounts `examples/nuxt/scala/zio/src/main/resources/sql` into PostgreSQL's initialization directory. For an empty database volume, PostgreSQL runs the example script to create this table:

```sql
CREATE TABLE IF NOT EXISTS h34s_notes (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  text text NOT NULL CHECK (length(trim(text)) BETWEEN 1 AND 2000)
);
```

Initialization scripts run only when the volume is empty. For an existing development database, apply the additive schema explicitly:

```sh
docker compose -f examples/nuxt/docker-compose.yml exec -T postgres sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' \
  < examples/nuxt/scala/zio/src/main/resources/sql/01-init.sql
```

The Notes request handlers never create or modify the schema. This script only initializes the example. Choose and run migrations explicitly for your own application.

## Run the application

Link the application, then start Nuxt with the database variables available:

```sh
sbt 'nuxtsvr/fastLinkJS' 'kyoExample/fastLinkJS'
pnpm dev
```

Restart an already-running Nuxt process if it did not receive those variables. In the prepared cloud environment, use its sbt launcher as described in [getting started](/guide/getting-started#prepared-cloud-environment).

## Create and read a note

After Nitro finishes building, run these requests from another terminal:

```sh
curl --fail -H 'Content-Type: application/json' \
  --data '{"text":"My first note"}' http://127.0.0.1:3000/api/notes
curl --fail http://127.0.0.1:3000/api/notes
```

POST returns status 201 with a note such as:

```json
{ "id": 1, "text": "My first note" }
```

GET returns an array ordered by ID. Existing rows can change the new note's ID. The `CreateNote` schema trims text and accepts lengths from 1 to 2000 characters. The handler uses `readBodyWithSchema`; blank, missing, null, or incorrectly typed text returns HTTP 422 with `Request body does not match schema`.

## Keep SQL in an application service

`examples/nuxt/scala/zio/src/main/scala/dev/yuri4n/svr/notes/Notes.scala` defines the service and implementation. Its queries are ordinary Skunk code:

```scala
import skunk.Session
import skunk.codec.all.*
import skunk.implicits.*
import zio.{Task, ZLayer}

final class NotesLive(session: Session[Task]) extends Notes:
    private val codec = (int4 *: text).to[Note]

    def create(value: String): Task[Note] =
      session.unique(sql"INSERT INTO h34s_notes (text) VALUES ($text) RETURNING id, text".query(codec))(value)

    def list: Task[List[Note]] =
      session.execute(sql"SELECT id, text FROM h34s_notes ORDER BY id".query(codec))

object NotesLive:
    val layer: ZLayer[Session[Task], Nothing, Notes] = ZLayer.fromFunction(new NotesLive(_))
```

The `Note` model and `Notes` trait appear in the [handler guide](/guide/handlers#define-the-data-you-exchange). Skunk's typed SQL interpolator uses `$text` as a parameter codec. The input value is bound separately; it is never concatenated into SQL.

Compose the service's dependencies in your application. For the Notes example, define `Services.layer` in `app/Services.scala`:

```scala
object Services:
    val layer: ZLayer[Any, Throwable, Notes] =
      DatabaseConfig.layer >>> DatabaseResource.layer >>> NotesLive.layer
```

Implement `DatabaseConfig` to load your settings and `DatabaseResource` to acquire and release the connection. The example uses Ciris for its five environment variables and wraps Skunk's `Session.single` in a scoped ZIO resource. Provide the composed layer around each endpoint through your own helper, as shown in [the `AppHandler` example](/guide/handlers#compose-services-once-in-application-code). These objects are application code; h34s does not supply them.

## Understand the connection lifetime

The current example opens one connection per request and closes it when the request completes or fails. It also acquires that connection before the handler validates its input. Reusing `Services.layer` does not memoize a shared connection or create an application-wide pool.

For pooling, own pool startup and shutdown in your application and scope each lease to the request or stream that uses it. This example does not yet implement or validate a pool. Transactions and migrations are also outside this small example; the repository's recovered migration helpers are experimental.

## Keep the Skunk Node integration

The pinned Skunk version calls `require('crypto')` during SCRAM authentication. Nitro runs ES modules, so `examples/nuxt/server/plugins/skunk-node-crypto.ts` installs Node's loader before requests arrive. Keep that plugin when copying this database example into another ESM application.

PostgreSQL's default SCRAM authentication stays enabled. If authentication ran before the plugin was installed, restart Nuxt: the failed library initializer cannot recover in the same process.

## Check requests and cleanup

With Nuxt and PostgreSQL running:

```sh
node scripts/smoke.mjs
```

This checks the stream route, performs one insert/read, and verifies safe responses for malformed and invalid input. It creates one note in the selected database. Set `H34S_BASE_URL` if Nuxt runs on a different local port.

The prepared environment also checked that no application connections remained after successful requests, invalid input, and a query failure. See [status](/reference/status) for validation limits.

To stop the local database without deleting its volume:

```sh
docker compose -f examples/nuxt/docker-compose.yml stop postgres
```
