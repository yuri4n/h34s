Read configuration from Scala. h34s decodes Nuxt `runtimeConfig` into your own case class, so you never touch `process.env` or JavaScript objects. Nitro applies `NUXT_*` environment overrides before h34s sees the values.

> **Status.** `RuntimeConfig` and `ZRuntimeConfig` are part of `0.2.0-SNAPSHOT` (unreleased). They need the h34s Nitro plugin, which the [`@yuri4n/h34s-nuxt` module](/guide/npm-tooling) registers.

## Declare the keys

Nuxt overrides only keys you declare. Give each one a safe development default and leave secrets empty:

```ts
export default defineNuxtConfig({
  modules: ['@yuri4n/h34s-nuxt'],
  runtimeConfig: {
    database: { host: '127.0.0.1', port: 5432, user: 'h34s', password: '', name: 'h34s' },
  },
})
```

Keys outside `runtimeConfig.public` never reach the browser.

## Define a Scala type

```scala
final case class DatabaseConfig(host: String, port: Int, user: String, password: Secret, name: String)
    derives NativeConverter

/** The part of the Nuxt runtime config that this application reads. Other keys are ignored. */
final case class AppConfig(database: DatabaseConfig) derives NativeConverter
```

This is the demo's `AppConfig.scala`. `Secret` comes from `dev.yuri4n.exts.kyoh3` or `dev.yuri4n.exts.zioh3`.

## Read it

| You need | Kyo | ZIO |
| --- | --- | --- |
| This request's config | `RuntimeConfig.get[AppConfig](request)` | `ZRuntimeConfig.get[AppConfig](request)` |
| The startup config, for pools and clients | `RuntimeConfig.load[AppConfig]` | `ZRuntimeConfig.load[AppConfig]` |

Use `load` inside `Shared` or `ZShared` ([lifetimes](/guide/lifetimes)): there is no request at startup.

## Override at runtime

Nitro maps each declared key to `NUXT_` plus its path in upper snake case: `database.password` becomes `NUXT_DATABASE_PASSWORD`, and `apiToken` becomes `NUXT_API_TOKEN`. Set secrets this way, at runtime.

Nitro 2.13 parses these values with `destr` before h34s reads them, so `5432` becomes a number and `true` a boolean. A numeric-looking secret such as `12345` arrives as a number, and a `Secret` field then fails to decode. This comes from Nitro's source; h34s has no test for it.

## When configuration is wrong

Every failure is a `ConfigError`, which is never shown to clients (an unhandled one is an opaque 500). Messages name only the path:

| Situation | Message |
| --- | --- |
| The Nuxt module is missing | `h34s Nitro plugin is not installed` |
| A field has the wrong type | `Nuxt runtime config does not match the expected shape at root.database.port` |
| Reading the config throws | `h34s could not read the Nuxt runtime config` |

A derived `NativeConverter` accepts a missing or `null` plain `String` field. Declare every key, or use a [schema](/guide/schema) type when a missing value must fail.

## Keep secrets secret

`Secret` prints as `Secret(<redacted>)`. `secret.reveal` returns the value; call it only where the value must leave your program, such as a database client. `secret.matches(candidate)` compares in constant time for a given length:

```scala
final case class AdminConfig(adminToken: Secret) derives NativeConverter

def isAdmin(request: Request, config: AdminConfig): Boolean =
  request.bearerToken.exists(config.adminToken.matches)
```

- Never log a revealed secret, put it in a `SafeError` message, or return it to a client.
- Never commit secret values. Supply them at runtime.
- Keep [debug mode](/guide/debugging) off in production: diagnostics include exception messages.

Tested: decoding, path-only errors, a throwing read, the missing plugin and the opaque 500, with fake plugin records (`RuntimeConfigSuite`, `ZRuntimeConfigSpec`, the demo's `AppConfigSpec`). In a production build of the demo, `ZRuntimeConfig.load` read the database settings and a marker password supplied at runtime stayed out of logs and responses. Each `NUXT_*` override has not been tested separately.
