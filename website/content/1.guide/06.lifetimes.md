Every resource needs an owner. h34s gives you two lifetimes:

| Lifetime        | Use it for                                         | Kyo                                     | ZIO                                 |
| --------------- | -------------------------------------------------- | --------------------------------------- | ----------------------------------- |
| One request     | A pooled session, a transaction, a stream's source | the request `Scope` in `HandlerEffects` | the request `Scope` in `HandlerEnv` |
| The application | A connection pool, an HTTP client                  | `Shared`                                | `ZShared`                           |

> **Status.** `Shared` and `ZShared` are part of `0.2.0-SNAPSHOT` (unreleased).

## Request resources

Acquire with Kyo's `Scope.acquireRelease` or ZIO's `ZIO.acquireRelease` inside the handler. h34s releases them:

- for a value or `Unit` body, after your program and before the response settles (asynchronous finalizers included);
- for a streamed body, after the stream ends, fails or is cancelled;
- when the client disconnects: h34s interrupts your program, waits for the finalizers, and writes nothing.

The demo takes at most one pooled Skunk session per request, on first use, so a request that fails validation never touches the pool:

```scala
object NotesLive:
    val layer: ZLayer[SessionPool & Scope, Nothing, Notes] =
      ZLayer.fromZIO(
        for
          pool    <- ZIO.service[SessionPool]
          scope   <- ZIO.service[Scope]
          session <- pool.session.provideEnvironment(ZEnvironment(scope)).memoize
        yield NotesLive(session),
      )
```

A failing Kyo `Scope` finalizer is logged and keeps the response. A ZIO finalizer that dies turns a value response into a 500. Put work that must affect the response in the program, not in a finalizer.

## When the client disconnects

If the client leaves before your handler finishes (a closed tab, an aborted `fetch`), Kyo and ZIO handlers behave the same way: h34s interrupts your program, runs your finalizers, waits for them (asynchronous ones too) before it reports the request as done, and writes nothing to the closed connection. Work forked with Kyo's `Async.timeout`, `race`, `gather`, `zip` or a concurrent `foreach`, and ZIO child fibers, also finish their cleanup first. Work on a fiber that nothing owns (Kyo's `Fiber.initUnscoped`) is not waited for.

Interruption can stop work you expected to finish: a database transaction can roll back instead of committing. Make a step that must complete uninterruptible:

- Kyo: `KHandler.uninterruptible(step)`. The request waits for the step, then releases earlier resources, then settles. Kyo's `Async.uninterruptible` alone does not make the request wait: the request settles and releases its resources while the step still runs.
- ZIO: `step.uninterruptible`, or `ZIO.uninterruptibleMask` to protect only part of it.

Keep those regions small: a disconnect cannot stop them, so h34s waits for them. Tests in both runtimes check that order. JavaScript work that has already started, such as a storage Promise, is not cancelled; h34s only stops waiting for it.

## Application resources

`Shared` and `ZShared` hold one resource for all requests:

- the first `get` acquires it, and concurrent first calls share one acquisition;
- a failed acquisition is not cached;
- a cancelled request does not cancel an acquisition others wait for;
- a successful acquisition registers with the Nitro close hook;
- `close` releases it; a later `get` acquires it again;
- a `close` during the first acquisition releases the value at once, and the waiting `get` calls fail instead of receiving it.

Declare one in an `object`. Nothing runs until the first `get`:

```scala
object Resources:
    val pool: Shared[Pool] = Shared(
      Scope.acquireRelease(openPool)(pool => closePool(pool)),
    )
```

`openPool`, `closePool` and `Pool` stand for your code. The Kyo demo builds its greeting service from the startup config this way:

```scala
val greetings: Shared[Greetings] = Shared(RuntimeConfig.load[KyoConfig].map(config => Greetings.live(config.greeting)))
```

For ZIO, wrap any layer, as the demo's `AppHandler` does:

```scala
private val database = ZShared.layer(SessionPool.layer)
```

Then `database.provide(program)` supplies it. Load settings inside the acquisition with `RuntimeConfig.load` or `ZRuntimeConfig.load`.

Every handler linked from the same sbt project shares one copy of a `Shared` value. Two separately linked projects have two copies.

## When Nitro closes

The h34s plugin releases every registered `Shared` and `ZShared` on Nitro's `close` hook; one failing release does not stop the others. In Nitro 2.13 the `node-server` preset calls that hook on `SIGTERM` and `SIGINT` (30-second graceful shutdown by default), and `nuxt dev` calls it when it replaces its worker. These facts come from Nitro's source. In a production build of the demo, `SIGTERM` released the `ZShared` pool and the server exited with status 0; the `nuxt dev` worker case has not been checked.

Without the plugin (for example in unit tests), nothing registers. Call `close` yourself.
