Use h34s as a toolbox inside your application. Write your handlers in Scala.js, define your models and services, resolve their dependencies, and mount the linked exports as Nuxt routes. Choose the ZIO or Kyo integration to supply request context and execute handler effects.

Private Maven artifacts are published under `dev.yuri4n` version `0.1.0-alpha.1`, with authenticated consumer checks in the [release workflow](https://github.com/yuri4n/h34s/actions/runs/38779659501). Follow the [release installation guide](https://github.com/yuri4n/h34s/blob/main/docs/releases.md). Reusable build and Nuxt development integration are published separately as [the npm package](/guide/npm-tooling) `@yuri4n/h34s-nuxt@0.1.0-alpha.1`. Source integration remains available.

## Start a new project

Create your Nuxt application with Nuxt's own setup tools, then follow [the integration steps below](#add-scala-handlers-to-an-existing-nuxt-app). Add only the h34s modules you need. h34s does not supply a project scaffold or a `create-h34s` command.

For a runnable reference, use the [getting started tutorial](/guide/getting-started). It runs the repository's example application: first request `/api/test` without a database, then try the [Notes example](/guide/database) for models, validation, service composition, and a PostgreSQL write. Cloning the repository is optional for package consumers.

The application in `examples/nuxt/` is a development playground and includes unrelated historical modules and content. Copy relevant patterns into your app rather than adopting its whole structure. The prepared checkout validates that example; the release workflow separately checks Maven consumers that compile, link, and serve h3 requests. Neither is a full fresh-project generator check.

## Add Scala handlers to an existing Nuxt app

Existing TypeScript handlers can stay in place. Add a Scala.js/sbt build alongside the Nuxt application, with a dedicated server module using ES-module output. Its development linking output goes to `server/.scala`.

The ZIO application needs one direct Maven dependency:

```scala
libraryDependencies += "dev.yuri4n" %%% "zio-h3-ext" % "0.1.0-alpha.1"
```

Its transitive modules correspond to these source projects:

| sbt project             | Responsibility                         |
| ----------------------- | -------------------------------------- |
| `h3Ext`                 | Native h3 bindings and facades         |
| `zioH3Ext`              | ZIO handler boundary and streaming     |
| `zioJsExt`              | ZIO/JavaScript helpers                 |
| `nativeConverterZIOExt` | Native conversions used by the ZIO API |

The [Kyo API](/guide/kyo) provides `kyo-h3-ext`, corresponding to `kyoH3Ext`, with a dependency on `h3-ext`. Resolve your application services through Kyo's `Env`, following its example; this API does not require a ZIO runtime or Schema dependency. Use Scala 3.9.0 for Kyo and Scala 3.5.2 for ZIO, with the shared Scala.js 1.22.0 linker. Check the [compatibility profile](/reference/compatibility#alpha-010-node24) for the complete toolchain.

A source checkout or submodule with explicit sbt project references is also an option when developing the libraries. Keep your application independent of the example's `nuxtsvr` services and recovered migration experiments. Install npm `h3@1.15.4` in the Nuxt app. Add `zio-h3-schema-ext` only when you want the integrated [schema reader](/guide/handlers#choose-your-decoding-approach).

Export each handler from Scala.js. The Notes GET example below uses an application-defined `AppHandler` and `Notes` service. Define your own composition helper as shown in the [handler guide](/guide/handlers#compose-services-once-in-application-code), or call `ZHandler.define` directly after providing your services; `AppHandler` is not an h34s export.

```scala
@JSExportTopLevel("default", "notes-get")
val listNotes = AppHandler.define:
    ZIO.serviceWithZIO[Notes](_.list)
```

Create `server/api/notes.get.ts` to mount that export:

```ts
export { default } from '../.scala/notes-get.js'
```

This mounting file is integration setup. The handler itself remains an ordinary ZIO program. Automated route discovery and mounting are planned.

Configure the [npm CLI and Nuxt module](/guide/npm-tooling) with the sbt project, generated output, and required entry files. Run `h34s-scala dev` before Nuxt, keep `h34s-scala watch` running during edits, and run `h34s-scala build` before the Nuxt production build. If several endpoints share service layers, provide them in an application helper such as `AppHandler`, following the [handler guide](/guide/handlers). The database example and its services are optional.

The same mounting pattern applies to Kyo exports. Follow the [Kyo guide](/guide/kyo) for its compiled `AppHandler` and standalone example; the ZIO Skunk example is not a Kyo database adapter.

The npm Nuxt module supplies the development-error plugin, development loader, and source-map integration. Enable source maps in your Scala.js build and Node command, as explained in the [debugging guide](/guide/debugging). These shared helpers no longer need copying into each application.

The release checks validate independent artifact consumers through real h3 requests. A full external Nuxt application still needs its own route, development-loading, and deployment validation. Avoid copying the playground's entire dependency set into an existing application.

## Add Nuxt to an existing Scala.js app

Create a dedicated Scala.js server module with ES-module output. Use the published h34s artifact or reference its source modules, mount exports in Nuxt, and keep your models and services in application modules.

Only Scala.js-compatible code can enter the Nitro bundle. Shared models can live in a cross-built module if they also serve a JVM application. Java and sbt remain build-time tools; the selected server runtime is Node.

For a JVM-only application, choose which code can be shared with Scala.js. You can keep the existing JVM backend and call it over HTTP. JDBC dependencies, including Doobie, cannot run inside a Scala.js handler. The h34s example uses Skunk directly in Nitro.

## Keep the boundaries visible

Keep database configuration, resource ownership, business services, and any `AppHandler` helper in your application. Choose your own model and persistence library. h34s handles requests and effect execution; it does not define or provide your application services.

The [architecture reference](/reference/architecture) explains these boundaries. Complete Nuxt consumer examples for all three paths, generated TypeScript wire types, and production packaging remain separate deliverables.
