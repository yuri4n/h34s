h34s keeps the same division of responsibilities across projects: Nuxt mounts the routes, Scala.js implements the handlers, and application modules supply their own models and services. Choose the ZIO or Kyo integration to own request context and effect execution.

The current integration is available as source in this repository. Published artifacts, an installation helper, and clean external-consumer checks are still [planned](/reference/status).

## Start a new project

Use the repository example and the [getting started guide](/guide/getting-started). First request `/api/test` without a database. Then add the [Notes example](/guide/database) to see models, validation, service composition, and a real PostgreSQL write.

This is the path exercised in the prepared development checkout. A fresh machine has not yet been validated. There is no `create-h34s` command or published dependency coordinate to install.

The recovered application includes unrelated playground modules and content. Treat the Notes example as the current reference for application code; do not assume every historical module is part of the intended library API.

## Add Scala handlers to an existing Nuxt app

Existing TypeScript handlers can stay in place. Add a Scala.js/sbt build alongside the Nuxt application, with a dedicated server module using ES-module output. Its development linking output goes to `server/.scala`.

Until releases exist, the ZIO integration needs source references to these projects:

| sbt project             | Responsibility                         |
| ----------------------- | -------------------------------------- |
| `h3Ext`                 | Native h3 bindings and facades         |
| `zioH3Ext`              | ZIO handler boundary and streaming     |
| `zioJsExt`              | ZIO/JavaScript helpers                 |
| `nativeConverterZIOExt` | Native conversions used by the ZIO API |

The [Kyo slice](/guide/kyo) provides `kyoH3Ext` with a dependency on `h3Ext`. A Kyo application uses those projects independently of the ZIO integration. Its example supplies application services through Kyo's `Env`; it does not require a ZIO runtime or Schema dependency. Check its [separate development profile](/reference/compatibility#kyo-dev-node24) before choosing a Scala compiler version.

A source checkout or submodule with explicit sbt project references is the interim approach. Keep your application independent of the example's `nuxtsvr` services and the recovered migration experiments. The current versions are listed in [status](/reference/status).

Export each handler from Scala.js. For example, the Notes GET endpoint uses:

```scala
@JSExportTopLevel("default", "notes-get")
val listNotes = AppHandler.define:
    ZIO.serviceWithZIO[Notes](_.list)
```

The current integration mounts that export in `server/api/notes.get.ts`:

```ts
export { default } from '../.scala/notes-get.js'
```

This mounting file is integration setup. The handler itself remains an ordinary ZIO program. Automated route discovery and mounting are planned.

Run Scala linking before Nuxt and keep a separate linking watch task during development. Define your own `AppHandler` to provide your service layers, following the [handler guide](/guide/handlers). The database example and its services are optional.

The same mounting pattern applies to Kyo exports. Follow the [Kyo guide](/guide/kyo) for its compiled `AppHandler` and standalone example; the ZIO Skunk example is not a Kyo database adapter.

Development diagnostics also need `server/plugins/h34s-development.ts`. Scala source maps need the `build/scala-source-maps.mjs` loader, the development-only `nitro:config` hook, and source maps enabled in Scala.js linking. Copying the handler modules alone does not enable those features; the [debugging guide](/guide/debugging) explains each part.

These steps describe the current integration boundary. An external Nuxt consumer has not yet been validated, so this is not a complete installation recipe. Avoid copying the playground's entire dependency set into an existing application.

## Add Nuxt to an existing Scala.js app

Create a dedicated Scala.js server module with ES-module output. Reference the h34s source modules, mount its exports in Nuxt, and keep your own models and services in application modules.

Only Scala.js-compatible code can enter the Nitro bundle. Shared models can live in a cross-built module if they also serve a JVM application. Java and sbt remain build-time tools; the selected server runtime is Node.

For a JVM-only application, choose which code can be shared with Scala.js. You can keep the existing JVM backend and call it over HTTP. JDBC dependencies, including Doobie, cannot run inside a Scala.js handler. The h34s example uses Skunk directly in Nitro.

## Keep the boundaries visible

`AppHandler` belongs to your application. Database configuration, resource ownership, and business services belong there too. The reusable library should not require an application model or a particular persistence abstraction.

The [architecture reference](/reference/architecture) explains these boundaries. Fresh consumer examples for all three paths, generated TypeScript wire types, and production packaging remain separate deliverables.
