# Adoption paths

h34s is a toolbox. You add a Scala.js server module to a Nuxt application, write handlers in Kyo (or ZIO), and mount them as Nuxt routes. Your models, services, configuration and resources stay in your application.

Pick the path that matches what you have:

1. [Start a new project](#1-start-a-new-project)
2. [Add Scala handlers to an existing Nuxt app](#2-add-scala-handlers-to-an-existing-nuxt-app)
3. [Add Nuxt to an existing Scala.js project](#3-add-nuxt-to-an-existing-scalajs-project)

Every path ends with the same steps: [write a handler, mount it, run it](#write-mount-and-run-a-handler).

## Get the libraries

**The API in these guides is `0.2.0-alpha.1`.** The older `0.1.0-alpha.1` has a different API; see the [migration guide](../2.reference/4.migration.md).

<!-- claude 2026-10-20: changed: GitHub Packages with a token, not a private registry (ADR-0013) -->

Install `0.2.0-alpha.1` from GitHub Packages with a GitHub token, as [Releases](../2.reference/2.releases.md) describes. Its [release workflow](https://github.com/yuri4n/h34s/actions/runs/39145732257) published the packages and verified them through the registry.

To build against h34s source changes that are not released, use one of these:

- Publish an h34s checkout to your local Ivy repository: run `sbt releasePublishLocal` in it (JDK 25), then depend on the version in its `version.sbt`. sbt resolves the local Ivy repository by default, before the registry, so remove that local copy before you depend on a registry release with the same version. This path has not been exercised by hand; the repository's own consumer check publishes to a temporary Maven directory instead.
- Reference the h34s source projects from your sbt build.

Pick the modules for your runtime. Kyo applications never need ZIO; ZIO applications get Kyo through the ZIO adapter:

| You want                 | Kyo                               | ZIO                                                               |
| ------------------------ | --------------------------------- | ----------------------------------------------------------------- |
| Handlers                 | `kyo-h3-ext`                      | `zio-h3-ext`                                                      |
| Schemas (optional)       | `native-converter-kyo-schema-ext` | `native-converter-zio-schema-ext` + `zio-schema-derivation` 1.7.5 |
| Nitro storage (optional) | `kyo-nuxthub-ext`                 | `zio-nuxthub-ext`                                                 |

On the npm side, every application needs `@yuri4n/h34s-nuxt` (a dev dependency) and `h3@1.15.4` (a runtime dependency). See [npm tooling](13.npm-tooling.md).

## Toolchain

| Tool             | Version        | Why                                                              |
| ---------------- | -------------- | ---------------------------------------------------------------- |
| JDK              | 25             | Runs sbt; Kyo 1.0.0-RC7 macros need it. Not needed in production |

## 2. Add Scala handlers to an existing Nuxt app

Keep your TypeScript handlers. Scala handlers live next to them and declare their own routes.

1. Add an sbt build at the Nuxt root, with your Scala sources in `scala-server/`, as in [Configure the Scala.js module](#configure-the-scalajs-module). Point its linker output at a generated directory such as `server/.scala`. If you keep a separate sbt build next to the app instead, set [`sbtRoot`](13.npm-tooling.md#point-the-cli-at-your-sbt-build) in `h34s.config.mjs`. <!-- claude 2026-10-20: changed: the sbt build at the Nuxt root, or sbtRoot for a separate build (ADR-0009) -->
2. Add `@yuri4n/h34s-nuxt` and `h3@1.15.4`, and register the module in `nuxt.config.ts`. See [npm tooling](13.npm-tooling.md).
3. Move only the routes you want to Scala. A TypeScript route and a Scala route can share a path prefix. Give each Scala route its own path and method: two handlers for the same route and method conflict.
4. Read your existing `runtimeConfig` keys from Scala with `RuntimeConfig` (Kyo) or `ZRuntimeConfig` (ZIO). See [configuration](05.configuration.md).

The h34s wire format wraps values in `{"data": ...}`. If existing clients expect the raw value, pass `HandlerOptions(success = SuccessEnvelope.Raw)` for those routes. `Raw` sends a string as `text/plain; charset=utf-8` and any other value as JSON (`application/json`), unless you set a content type.

## 3. Add Nuxt to an existing Scala.js project

<!-- claude 2026-10-20: changed: the Nuxt app in web/ below the sbt build, with h34s.sbt and sbtRoot (layout B, ADR-0009) -->

Keep your sbt build where it is, and put the Nuxt application in `web/` below it. Your `build.sbt` does not change: the h34s settings go in a new `h34s.sbt` next to it, and sbt loads both files.

**Status.** `sbtRoot` is new in `@yuri4n/h34s-nuxt` `0.3.0-alpha.1`, which is not released yet. With `0.2.0-alpha.1`, create the Nuxt application at the root of your sbt build instead, as in path 1, and keep the h34s settings in `h34s.sbt` with the linker output `server/.scala`.

1. Create a Nuxt 4 application in `web/` with Nuxt's own tooling.
2. Check `project/`. If no file there adds `sbt-scalajs` 1.22.0 or later, add or update the line from [Configure the Scala.js module](#configure-the-scalajs-module). If `.jvmopts` is missing, add it from the same section.
3. Create `h34s.sbt` next to `build.sbt`, with a dedicated server module that links into `web/server/.scala`:

   ```scala
   // h34s.sbt
   import org.scalajs.linker.interface.{ModuleKind, OutputPatterns}

   lazy val server = project.in(file("scala-server"))
     .enablePlugins(ScalaJSPlugin)
     .settings(
       scalaVersion := "3.9.0",
       libraryDependencies += "dev.yuri4n" %%% "kyo-h3-ext" % "0.2.0-alpha.1",
       scalaJSLinkerConfig ~= (_.withModuleKind(ModuleKind.ESModule)
         .withOutputPatterns(OutputPatterns.fromJSFile("%s.js"))),
       Compile / fastLinkJS / scalaJSLinkerConfig ~= (_.withSourceMap(true)),
       Compile / fastLinkJS / scalaJSLinkerOutputDirectory :=
         (LocalRootProject / baseDirectory).value / "web" / "server" / ".scala",
       Compile / fullLinkJS / scalaJSLinkerOutputDirectory :=
         (LocalRootProject / baseDirectory).value / "web" / "server" / ".scala",
     )
   ```

   Keep your models and services in their own modules. To use one from the server module, add `.dependsOn(LocalProject("core"))`, with the ID of your project instead of `core`. If your build already has a project named `server`, pick another name and use it in `h34s.config.mjs`.

4. In `web/`, add the npm package, the Nuxt module and the scripts, as in [npm tooling](13.npm-tooling.md).
5. Create `web/h34s.config.mjs` with `sbtRoot: '..'`, so that `h34s-scala` runs sbt in your build:

   ```js
   import { defineConfig } from '@yuri4n/h34s-nuxt/build'

   export default defineConfig({
     sbtRoot: '..',
     modules: [{ project: 'server', output: 'server/.scala' }],
   })
   ```

6. [Write, mount and run a handler](#write-mount-and-run-a-handler). Put the handler in `scala-server/src/main/scala/`, skip the step that writes `h34s.config.mjs`, and run the scripts in `web/`.

Only Scala.js-compatible code can enter Nitro. Your shared models must cross-build for Scala.js. Use Scala 3.9.0 for the modules that h34s handlers depend on.

If your backend is JVM-only, you have two choices: cross-build the models and services that can run on Scala.js, or keep the JVM server and call it over HTTP from Nuxt. JDBC libraries, including Doobie, do not run in Scala.js. For PostgreSQL inside Nitro, use kyo-sql or Skunk; see [databases](08.database.md).

Create `.jvmopts` next to `build.sbt`, with the JVM options for sbt:

<!-- tour: .jvmopts -->

```text
-Xss4m
-Xmx4g
```

The repository's own builds use these options, and its fresh-consumer check (`scripts/check-consumers.mjs`) copies the same file into each consumer project. A build without them has not been tested.

<!-- tour: build.sbt -->

```scala
// build.sbt
import org.scalajs.linker.interface.{ModuleKind, OutputPatterns}

lazy val server = project.in(file("scala-server"))
  .enablePlugins(ScalaJSPlugin)
  .settings(
    scalaVersion := "3.9.0",
    libraryDependencies += "dev.yuri4n" %%% "kyo-h3-ext" % "0.2.0-alpha.1",
    scalaJSLinkerConfig ~= (_.withModuleKind(ModuleKind.ESModule)
      .withOutputPatterns(OutputPatterns.fromJSFile("%s.js"))),
    Compile / fastLinkJS / scalaJSLinkerConfig ~= (_.withSourceMap(true)),
    Compile / fastLinkJS / scalaJSLinkerOutputDirectory :=
      (LocalRootProject / baseDirectory).value / "server" / ".scala",
    Compile / fullLinkJS / scalaJSLinkerOutputDirectory :=
      (LocalRootProject / baseDirectory).value / "server" / ".scala",
  )
```

For ZIO, replace `kyo-h3-ext` with `zio-h3-ext`. Run sbt with JDK 25.

`OutputPatterns.fromJSFile("%s.js")` makes each exported module a `<name>.js` file, which Nitro mounts. Keep only generated files in `server/.scala`: a production build clears it.

## Write, mount and run a handler

1. Write a handler, export it as the `default` export of its own module, and give it a route with `.at`:

   ```scala
   import dev.yuri4n.exts.kyoh3.*
   import org.getshaka.nativeconverter.NativeConverter

   import scala.scalajs.js.annotation.JSExportTopLevel

   final case class Greeting(message: String) derives NativeConverter

   @JSExportTopLevel("default", "hello-get")
   val hello: EventHandler = KHandler.define(_ => Greeting("Hello from Scala")).at(Route.get("/api/hello"))
   ```

2. Point `h34s.config.mjs` at the linked output:

   <!-- tour: h34s.config.mjs -->

   ```js
   import { defineConfig } from '@yuri4n/h34s-nuxt/build'

   export default defineConfig({
     modules: [{ project: 'server', output: 'server/.scala' }],
   })
   ```

3. Link and start Nuxt with the scripts from [npm tooling](13.npm-tooling.md): `pnpm dev:scala`. The link step prints `[h34s] 1 route and 0 models in server/.scala`. <!-- claude 2026-10-20: changed: the link step also counts the models (ADR-0014) -->
4. Request `http://127.0.0.1:3000/api/hello`. Expected body: `{"data":{"message":"Hello from Scala"}}`.

You write no route file: the Nuxt module mounts the route from the manifest that `h34s-scala` writes after linking, and `$fetch('/api/hello')` is typed from the generated declaration. `derives NativeConverter` types the body as `unknown`; derive `NativeSchema` from a schema to get its fields. See [routes and typed `$fetch`](02.routes.md).

If the request returns 404, check that the link step printed the route; if Nuxt warns that `server/.scala/h34s-routes.json` is missing, link first and restart Nuxt. If Nitro cannot resolve `h3`, add `h3@1.15.4` to your app's dependencies.

## Grow from there

- Wire your services in one `AppHandler`: [Kyo](03.kyo.md#compose-services-in-your-apphandler) or [ZIO](04.zio.md#compose-services-in-your-apphandler).
- Read [configuration](05.configuration.md) and keep secrets in `Secret`.
- Hold pools in `Shared` / `ZShared`: [lifetimes](06.lifetimes.md).
- Validate input with [schemas](07.schema.md).
- Add [streaming](09.streaming.md), [storage](11.storage.md), [tests](10.testing.md) and a [database](08.database.md).

## What is verified

The repository's consumer check builds four fresh sbt projects (Kyo, ZIO, Kyo Schema, ZIO Schema) against a temporary Maven repository and serves real h3 requests. A complete Nuxt application created from scratch with these steps has not been verified yet, on any path.
