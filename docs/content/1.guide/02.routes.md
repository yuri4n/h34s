# Routes and typed `$fetch`

Mount your Scala handlers from Scala, and let Nuxt type the calls to them. You write no route file in `server/api` and no TypeScript interface for the `{ data }` and `{ errors }` bodies.

## Mount a handler

1. Export each handler as the `default` export of its own Scala.js module, as before. The module ID becomes the linked file name.
2. Give the handler a route with `.at(...)`:

   ```scala
   import dev.yuri4n.exts.kyoh3.*
   import scala.scalajs.js.annotation.JSExportTopLevel

   @JSExportTopLevel("default", "notes-get")
   val listNotes: EventHandler = AppHandler.define(NotesHandler.list).at(Route.get("/api/notes"))

   @JSExportTopLevel("default", "notes-post")
   val createNote: EventHandler = AppHandler.define(NotesHandler.create).at(Route.post("/api/notes"))
   ```

   With a braceless handler function, put `.at` on its own line after the function:

   ```scala
   @JSExportTopLevel("default", "kyo-greeting-post")
   val personalizedGreeting: EventHandler = AppHandler
     .define: request =>
         for
           input    <- request.body.json[GreetingRequest]
           greeting <- Env.use[Greetings](_.greet(input.name))
         yield greeting
     .at(Route.post("/api/kyo/greeting"))
   ```

3. Link with `h34s-scala dev` (or `build`). The command prints how many routes it found.
4. Start Nuxt. The h34s Nuxt module mounts every route. Request it, for example `GET /api/notes`.

`Route.get`, `post`, `put`, `patch`, `delete`, `head` and `options` match one method. `Route.any(path)` matches every method, and `Route(Method.Patch, path)` takes the method as a value. Paths use Nitro's syntax: `/api/notes`, a parameter in `/api/notes/:id` (read it with `request.param("id")`), and a last segment `**` for the rest of the path. A path that does not start with `/`, or that contains spaces, `?`, `#`, `\` or an empty segment, fails when the module loads, so `h34s-scala` reports it at link time.

The ZIO API is the same: `ZHandler.define(program).at(Route.get("/api/notes"))`, with `Route` from `dev.yuri4n.exts.zioh3`.

`.at` returns a new handler and leaves the original unchanged. One linked module mounts one route: export a separate module for each method of a path.

## What h34s does with your routes

After linking, `h34s-scala build`, `dev` and `watch` load your linked modules in a separate Node process and read the route and response types of each default export. Then they write two kinds of files into each Scala.js output directory:

- `h34s-routes.json`, the route manifest: the module, route and method of each mounted handler.
- `<module>.d.ts` next to each handler module, for example `server/.scala/notes-get.d.ts`. It declares the module's default export with its real response body.

The Nuxt module reads the manifests and registers each route with Nitro (`nitro.handlers`) as a lazy handler: the module loads on its first request. Nitro's `routeRules` apply to these routes as to any other. In development, Nuxt loads the linked files directly with their source maps, as before.

Loading the modules runs their top-level code. Keep top-level handler values free of side effects: build resources in `Shared` or `ZShared`, which acquire on first use, and read configuration inside the handler or the shared resource.

When a route is added, removed or changed while `nuxt dev` runs, the next link writes a new manifest and Nuxt reloads its server routes without a restart. A code change alone reloads the Nitro worker, as before. The Scala.js linker deletes the generated files while it links; `h34s-scala` writes them again right after, and Nuxt keeps the previous routes until it does.

## Call your routes with typed `$fetch`

Nuxt types `$fetch` and `useFetch` from the generated declarations:

```ts
const { data } = await $fetch('/api/notes')
// data: { id: number; text: string }[]
const created = await $fetch('/api/notes', { method: 'POST', body: { text: 'Hello' } })
// created.data: { id: number; text: string }
```

<!-- claude 2026-10-19: changed: a Raw value that converts to null is typed as undefined -->
The type includes the handler's envelope from `HandlerOptions`: `{ data: T }` by default, `T` with `SuccessEnvelope.Raw`. A `Unit` body has no content, and a stream is text (`string`). With `Raw`, a value that converts to `null` is sent as 204 without a body, so `$fetch` returns `undefined`: an `Option[Int]` is typed `number | undefined`, not `number | null`.

Errors do not take part in Nitro's types. Each declaration exports the error body as `ErrorBody`, in the handler's `ErrorEnvelope`:

```ts
import type { ErrorBody } from '~~/server/.scala/notes-post'

await $fetch('/api/notes', {
  method: 'POST',
  body: { text: '' },
  onResponseError({ response }) {
    const body: ErrorBody = response._data
    // body.errors: { message: string; path?: string }[]
  },
})
```

`debug` appears only on internal errors in development or debug mode. See [debugging](12.debugging.md).

## Where the types come from

h34s writes the type of what your converter really writes, not a type guessed from the Scala class:

- A `NativeSchema` type (Kyo Schema or ZIO Schema) gives its fields with their wire names, optional fields as `T | null` (Kyo: may also be absent), collections as arrays, string-keyed maps as `Record<string, T>`, and sealed traits and enums as one-key objects or objects with the `@discriminator` field. The Kyo bridge also checks the type against its encoder with sample values; see [schemas](07.schema.md#typescript-types).
- native-converter's built-in converters give theirs: `String`, `Char` and `Long` are strings (native-converter writes `Long` as text), the other numbers are numbers, `Boolean` is a boolean, and `List`, `Vector`, `Seq`, `Set`, `Iterable`, `Array`, `Option` and `Map[String, A]` follow their elements.
- Any other converter, such as `derives NativeConverter` or a hand-written one, gives `unknown`. Mix `WireType.Described` into your own converter to type it:

  ```scala
  given NativeConverter[Email] = new NativeConverter[Email] with WireType.Described:
    val wireType = WireType.StringValue
    extension (email: Email) def toNative: js.Any = email.value
    def fromNative(state: ParseState): Email = Email(state.json.asInstanceOf[String])
  ```

  Check your declared type in a test with `wireType.describes(value)`.

`unknown` is safe: TypeScript makes you check the value before you use it. h34s never writes a type that the converter might not follow.

## Mount a handler with a route file instead

The one-line route file still works, for example when you prefer Nuxt's file layout for a route:

```ts
// server/api/notes.get.ts
export { default } from '../.scala/notes-get.js'
```

Leave `.at` off that handler, or remove the route file when you add `.at`: Nitro would register both. The declaration next to the linked module also types the route file. Keep `entries` in `h34s.config.mjs` for outputs that have only such handlers, so that `h34s-scala` checks the linked files; without `entries`, an output must contain at least one h34s handler.

## Troubleshooting

- **404 for a Scala route.** Run `h34s-scala dev` and check that it prints your route. If Nuxt says that `h34s-routes.json` is missing, it started before the first link: link, then restart Nuxt.
- **`Two Scala.js handlers mount GET /api/x`.** Two exports have the same route and method. Change one route or method.
- **`... has no h34s handlers`.** No module in that output has a default export from `KHandler.define` or `ZHandler.define`. Export one, or list `entries` for route files.
- **`Could not load the linked Scala.js module`.** A module's top-level code failed while `h34s-scala` loaded it. The message names the module and shows the stack (with Scala lines after `dev`, which links with source maps).
- **A response is `unknown`.** Its converter does not describe itself. Derive `NativeSchema`, or mix in `WireType.Described`.
- **`Cannot find module 'h3'` in a declaration.** Add `h3@1.15.4` to your app's dependencies, as the linked modules need anyway.

## Limits

- Nitro types response bodies only. Request bodies and query strings have no generated type.
- Only default exports are mounted. A module ID can hold one route.
- Generated types are recreated on each link. In development, your editor can show untyped calls for a moment while the linker runs.
