# Streaming and cancellation

Send a stream with `Response.sendStream`, and h34s writes its elements as they are produced. The request scope stays open until the stream ends, so the resources that the stream needs stay alive. When the client goes away, h34s stops the stream and waits for its cleanup.

**Status.** `Response.sendStream` and `Sent` are new in `0.3.0-alpha.1`, in both runtimes. They replace the stream bodies of `0.2.0-alpha.1`, which you returned from the handler, and `ZHandler.sendStream` of `0.1.0-alpha.1`, which had another signature. See the [migration guide](../2.reference/4.migration.md).

## Send a stream

Make `Response.sendStream(stream)` the last step of your handler, and return the `Sent` value that it gives. `Sent` is the handler's body: it tells h34s that the response is already on its way, so h34s writes nothing more.

Kyo: send a `kyo.Stream[String, S]`, where `S` needs at most `Async & Abort[Throwable] & Scope`:

```scala
val letters: EventHandler = KHandler.define: _ =>
    Response.status(Status.Accepted)
      .andThen(Response.header("content-type", "text/plain"))
      .andThen(Response.sendStream(Stream.init(Seq("a", "b", "c"))))
```

ZIO: send a `ZStream[Any, E, String]`, where `E <: Throwable` (or `Nothing`):

```scala
val letters: EventHandler = ZHandler.define(_ =>
  Response.status(Status.Accepted) *> Response.header("content-type", "text/plain") *> Response.sendStream(ZStream("a", "b", "c")),
)
```

Both send `abc` with status 202. These snippets come from the stream tests ("the guide's example sends abc with status 202" in `HttpStreamSuite` and `HttpStreamSpec`).

A returned stream does not compile. The compiler names the fix:

```text
h34s cannot send kyo.Stream[String, Any] as a response body. Return a value with a NativeConverter,
return Unit for a 204, or end the handler with Response.sendStream(stream) to stream text.
```

Call `sendStream` once. A second call is a defect: the first stream stays the response, and the server logs the failure.

## Know what is written

- **The head leaves at the call.** `sendStream` writes the head as your program set it when you call it. Over a Node socket, h34s also flushes it at once, so the client has the status and the headers before the first element. Without a socket, h34s writes the head first too (see [in-process calls](#in-process-calls)).
- **Set the head first.** Set the status, headers and cookies before you call `sendStream`. After the call, the status is fixed.
- **Elements are strings.** Each one is written as UTF-8 text, as is: no envelope and no separator. Node can write only strings and bytes to a response, so h34s does not accept other element types. A `null` element fails the stream.
- **Default content type.** Without a content type, h34s sends `text/plain; charset=utf-8` and `X-Content-Type-Options: nosniff`. Set `content-type` yourself for another format.
- **The marker.** Every streamed response carries `x-h34s-stream: 1`, so a server-side `$fetch` can tell a stream from a buffered body.
- **Your encoding.** Encode values yourself, one string per element. For newline-delimited JSON: `stream.map(value => value.toJson + "\n")` (`toJson` comes with `NativeConverter`) and `Response.header("content-type", "application/x-ndjson")`. Server-Sent Events work the same way.
- **Chunks.** HTTP clients can merge or split writes. Do not rely on one client-side chunk per element.

## Validate and acquire before the call

Because the head leaves at the call, a failure after it cannot change the status. Do the work that can fail with a proper error before you call `sendStream`:

1. Read and validate the request body.
2. Acquire the resources that the stream needs, such as a database session or a file.
3. Set the status and the headers.
4. Call `sendStream`.

A failure in steps 1 to 3 uses the normal [failure rule](03.kyo.md#fail-safely): the client gets an approved `SafeError` response or an opaque 500.

## Keep resources alive for the transfer

Acquire what the stream needs in the request scope, then send the stream. h34s keeps the scope open until the stream ends, fails or is cancelled:

- Kyo: `Scope.acquireRelease(open)(close).map(source => Response.sendStream(...stream over source...))`, or use a stream that manages its own resources.
- ZIO: `ZIO.acquireRelease(open)(close).flatMap(source => Response.sendStream(ZStream...))` in the handler (the request `Scope` is in `HandlerEnv`), or `ZStream.unwrapScoped(...)` / `ZStream.acquireReleaseWith(...)` for resources the stream owns.

A resource that you close before you call `sendStream` is gone. h34s cannot restore it.

## Cancellation

The bridge is pull-driven. One producer fiber owns the stream and advances only when the HTTP side asks for the next chunk. No chunk is computed before it is requested.

When the client disconnects:

1. h34s interrupts the producer and the handler.
2. It waits for the stream's finalizers, including asynchronous ones, and for the finalizers of every scope around `sendStream`.
3. It closes the request scope and its resources, once, writes nothing more, and only then settles the request.

A request whose response closed before the stream started never starts the stream. Interrupted work can roll back. To make a step finish anyway, use `KHandler.uninterruptible(step)` (Kyo) or `ZIO.uninterruptible` (ZIO); see [when the client disconnects](06.lifetimes.md#when-the-client-disconnects).

## Failures

| When it fails                                          | Result                                                                                                                                                                                                                                                                          |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Before `sendStream`                                    | The normal [failure rule](03.kyo.md#fail-safely): an approved `SafeError` response, or an opaque 500                                                                                                                                                                            |
| The stream, before or after its first element          | The head is already out. h34s closes the connection without a final chunk, so the client sees an incomplete transfer; the elements already written stay. `sendStream` fails with the stream's error, your program sees it, and the server logs it once. Nothing more is written |
| The stream throws, even a `SafeError`, or emits `null` | A defect of the stream: the same as above. The client never sees the error's text                                                                                                                                                                                               |
| Writing to the response                                | h34s closes the connection. The log names the write error, not the producer's interruption                                                                                                                                                                                      |
| The stream, without a socket (an in-process `$fetch`)  | The caller's read of the body fails after the elements it already read. `sendStream` fails with the stream's error                                                                                                                                                              |

Clients should treat an incomplete transfer as a failure, even when the status was successful.

## Roll back when a stream fails

`sendStream` fails with the stream's error, so the code around it sees the failure. Put a transaction, or a finalizer that checks the outcome, around the step.

In these snippets, `commit` and `rollback` are your own steps. With kyo-sql, `DB.transaction` around the step does this for you.

Kyo: a `Scope.run` around the step gives its finalizers the outcome, `Absent` on success:

```scala
Scope.run(
  Scope.ensure((outcome: Maybe[Result.Error[Any]]) => if outcome.isEmpty then commit else rollback)
    .andThen(Response.sendStream(stream)),
)
```

ZIO: `ZIO.addFinalizerExit`, inside `ZIO.scoped` or in the request `Scope`, gets the `Exit`:

```scala
ZIO.scoped(
  ZIO.addFinalizerExit(exit => if exit.isSuccess then commit else rollback) *> Response.sendStream(stream),
)
```

The stream's own cause reaches your ZIO program: a `ZStream[Any, MyError, String]` fails `sendStream` with `MyError`. The tests "a stream failure after two elements fails the sendStream step; a Scope finalizer around it sees the failure" (`HttpStreamSuite`) and "a stream failure after two elements fails the sendStream effect; a finalizer of ZIO.scoped around it sees the failure" (`HttpStreamSpec`) prove both. A client disconnect still waits for the finalizers of such a scope: see the test "a disconnect waits for the asynchronous finalizers of a Scope.run around sendStream before the request settles" (`HttpStreamSuite`).

## In-process calls

<!-- claude 2026-10-20: created: the measured in-process behavior (spike memo, sections 2.1 to 2.4; ADR-0004, ADR-0008) -->

Nitro answers a server-side `$fetch` to your own route in-process, without a socket. A stream works there too:

- **Head first.** h34s writes the head, hands the stream to h3, and settles h3's handler promise at once, so the caller gets the head before the first element. With the h34s test copy of Nitro 2.13.1's local fetch, a caller had the head after 16 to 23 ms and the elements one per 200 ms after that.
- **Bytes.** Chunks are UTF-8 bytes, because a Web `Response` body accepts only `Uint8Array` chunks.
- **Lifetime.** Your program and the request scope stay open until the caller reads the body to its end or cancels it.
- **A cancel waits for cleanup.** A `KHandler.$fetch` caller cancels an unread body when its `Scope` closes. The cancel waits until the callee's stream and request finalizers have run, so the caller settles after the callee's cleanup.
- **An unread body stays open.** A JavaScript caller, or a socketless Nitro preset, that drops the body without cancelling it keeps the callee's program and request scope open. h34s has no idle timeout for this case yet.

`NitroLocalFetchSuite` measures this behavior: "(b) streamed Scala route in-process: $fetch returns head-first; the body is pulled in the caller's Scope", "(c) a caller that drops a Streamed body: its Scope cancels the callee, whose finalizers run before the caller settles" and "(c) a caller that reads part of a Streamed body: the rest is cancelled when its Scope closes". The same suite shows the head arriving before the first element over real HTTP: "(b) the same streamed route over real HTTP: the head arrives before the first element".

## Test a streaming handler

`KHandler.test` and `ZHandler.test` collect what your handler sends. The result's body is `TestResponse.Body.Streamed(elements)`; see [testing](10.testing.md#test-a-streaming-handler).

## Limits

| Area                                                                                             | Behavior                                                                                                                                                                                               |
| ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Direct Node HTTP responses                                                                       | Supported. Tested with real h3 and mocked Node responses, and with a real `node:http` server in `NitroLocalFetchSuite`                                                                                 |
| No socket (Nitro's in-process local fetch, for example a server-side `$fetch` to your own route) | Supported. Tested with a copy of Nitro 2.13.1's local-fetch wiring (`NitroLocal`); not yet tested against `nuxt dev` or a built Nitro server. An unread body that nobody cancels keeps the callee open |
| Back pressure                                                                                    | One chunk at a time from your stream. h3's sink does not wait for Node's `drain`, so a slow client can still grow Node's output buffers. There is no end-to-end memory bound                           |
| Other Nitro presets (serverless, edge)                                                           | Not tested. Many of them serve every request without a socket, so no disconnect reaches h34s unless the platform cancels the body                                                                      |

## What is tested

Kyo `StreamSuite`, `HttpStreamSuite` and `NitroLocalFetchSuite`, ZIO `StreamSpec` and `HttpStreamSpec`: pull-driven delivery, the head written and flushed at the call before the first element, empty streams, order of effectful, concatenated, filtered and mapped streams, finalization exactly once after the end, cancellation waiting for asynchronous finalizers, disconnects releasing stream and request resources once (also with a `Scope.run` around `sendStream`), failures before and after the first element (the step fails, the connection closes, one log line), thrown errors and `null` elements, a failed write, the default content type, the socketless path (head first, UTF-8 bytes, a cancel that waits for the request, a failure that errors the caller's reads), and the compile error for a returned stream. A real client abort against a running Nuxt server has not been tested on this branch.
