# Share Nuxt build tooling through npm

`@yuri4n/h34s-nuxt` owns the reusable JavaScript build and development integration. Applications configure their Scala.js modules once, then use its `h34s-scala` CLI and Nuxt module. They do not copy build scripts, source-map loaders, or Nitro plugins.

**[`@yuri4n/h34s-nuxt@0.2.0-alpha.1` is published](https://github.com/yuri4n/h34s/releases/tag/npm-v0.2.0-alpha.1)** in the private GitHub npm registry. Its `npm-v0.2.0-alpha.1` tag is separate from the Maven [`v0.2.0-alpha.1`](https://github.com/yuri4n/h34s/releases/tag/v0.2.0-alpha.1) release; both tags point at the same commit. The older [`@yuri4n/h34s-nuxt@0.1.0-alpha.1`](https://github.com/yuri4n/h34s/releases/tag/npm-v0.1.0-alpha.1) stays published for the `0.1.0-alpha.1` libraries.

**Use the package version that matches your Scala libraries.** Install `@yuri4n/h34s-nuxt@0.2.0-alpha.1` with the `0.2.0-alpha.1` Scala libraries. The Kyo core reads runtime config, storage and the close hook from the package's new Nitro plugin. The `0.1.0-alpha.1` package only supplies the development flag, so with it `RuntimeConfig`, `KHubKv.mount` and their ZIO versions fail with `ConfigError("h34s Nitro plugin is not installed")`, and `Shared` resources are not released when Nitro closes.

## Install the tooling

The package is a build-time dependency. Keep `h3` as an application runtime dependency and Scala libraries as sbt/Maven dependencies; [Releases](../2.reference/2.releases.md) documents the latter.

Configure the private GitHub npm registry in the application's `.npmrc`:

```ini
@yuri4n:registry=https://npm.pkg.github.com
//npm.pkg.github.com/:_authToken=${GITHUB_PACKAGES_TOKEN}
```

Provide `GITHUB_PACKAGES_TOKEN` from your shell or secret manager using a classic PAT with `read:packages` and access to the private package. Commit only the environment-variable placeholder. This npm scope mapping does not configure sbt's Maven resolver.

In GitHub Actions, save the token as `PACKAGES_READ_TOKEN` and map `${{ secrets.PACKAGES_READ_TOKEN }}` into the `GITHUB_PACKAGES_TOKEN` process environment variable. Save the username as `PACKAGES_USER` when the same workflow also resolves Maven artifacts. GitHub reserves `GITHUB_` for saved secret and variable names.

Install the package and h3 with the version of your Scala libraries:

```sh
pnpm add -D @yuri4n/h34s-nuxt@0.2.0-alpha.1
pnpm add h3@1.15.4
```

With the older `0.1.0-alpha.1` Scala libraries, install the matching package instead: `pnpm add -D @yuri4n/h34s-nuxt@0.1.0-alpha.1`.

For local source review, run this from the h34s checkout:

```sh
npm pack ./packages/nuxt --pack-destination /tmp
```

Then install the resulting tarball in a disposable consumer:

```sh
pnpm add -D /tmp/yuri4n-h34s-nuxt-0.2.0-alpha.1.tgz
```

The repository example uses the local package. A packed-tarball check verifies that consumers receive the runtime plugin and helpers without referencing files outside the package. A local tarball path is a review setup; use the pinned registry dependency for an independently installable application.

Run `pnpm test:package` after installing the repository dependencies to verify the archive in an isolated consumer and a real Nuxt development/production server. The HTTP check covers development diagnostics, Scala source maps, relinking, routes mounted from the route manifest (typed, and added while Nuxt runs), and a production bundle that runs without the original generated files. It also builds the consumer with `scalaPrerender: 'stub'`: the prerender bundle must get the stub, the server output must keep the linked code, and a prerendered route that calls a Scala.js route must stop the build. <!-- claude 2026-10-19: changed: the scalaPrerender checks (review F2) -->

For `0.2.0-alpha.1`, the [successful npm release workflow](https://github.com/yuri4n/h34s/actions/runs/39144809255) downloaded the published archive with registry authentication, compared its bytes with the tested tarball, and installed that download offline in a clean consumer. It checked the CLI and all three JavaScript entry points without installing Nuxt as a peer. The [release](https://github.com/yuri4n/h34s/releases/tag/npm-v0.2.0-alpha.1) attaches the tarball and `registry.json`, which records its stable registry URL and integrity. The [`0.1.0-alpha.1` workflow](https://github.com/yuri4n/h34s/actions/runs/38937318206) ran the same checks for that version.

Nuxt 4.3.1 passes the packed-package development and production HTTP checks in CI, including the `0.2.0-alpha.1` release workflow. Nuxt 4.4.2 passed the same checks locally on Linux x86_64 with Node 24.19.0 for `0.1.0-alpha.1`; h34s's own checks have not repeated that profile for `0.2.0-alpha.1`. Package-level tests also cover Node 22.18.0 and 24. These results establish those explicit profiles, not every Nuxt 4.x version or a Nix/NixOS build.

## Configure the Scala.js outputs

Create `h34s.config.mjs` beside the application's `package.json`:

```js
import { defineConfig } from '@yuri4n/h34s-nuxt/build'

export default defineConfig({
  modules: [
    {
      project: 'server',
      output: 'server/.scala',
    },
  ],
})
```

`project` is the sbt project ID, not a filesystem directory. Omit it for a root-project task such as `fullLinkJS`. `output` is the generated directory relative to the application root. Add another module for an independent Kyo application if needed. Each module needs its own generated output directory.

`entries` is optional. Without it, an output must contain at least one h34s handler (a default export from `KHandler.define` or `ZHandler.define`). List `entries: ['notes-get.js']` when an output has only modules that you mount with route files; the CLI then checks that linking produced each file.

Keep only generated files in these directories: the production command removes previous output before linking. Do not point `output` at a source directory or an application root.

The package does not change `build.sbt`. Configure both linking modes to emit into the same directory and enable development source maps. For an sbt server project, these settings are relative to the root sbt build:

```scala
import org.scalajs.linker.interface.ModuleKind

// Inside the Scala.js server project's .settings(...):
scalaJSLinkerConfig ~= (_.withModuleKind(ModuleKind.ESModule)),
Compile / fastLinkJS / scalaJSLinkerConfig ~= (_.withSourceMap(true)),
Compile / fastLinkJS / scalaJSLinkerOutputDirectory :=
  (LocalRootProject / baseDirectory).value / "server" / ".scala",
Compile / fullLinkJS / scalaJSLinkerOutputDirectory :=
  (LocalRootProject / baseDirectory).value / "server" / ".scala",
```

The npm package requires Node 22.18 or later and Nuxt 4.3.1 or 4.4.2. These are explicit compatibility profiles; other Nuxt versions need validation. Use the compiler, linker, and JDK versions from the [toolchain profile](../2.reference/2.releases.md#toolchain); the combined repository profile uses Node 24. The package does not install Java or sbt.

### Point the CLI at your sbt build

**Status.** `sbtRoot` is new in `@yuri4n/h34s-nuxt` `0.3.0-alpha.1`, which is not released yet. `0.2.0-alpha.1` ignores the key and runs sbt in the application root.

`sbtRoot` is optional. It names the directory of your sbt build, where `h34s-scala` runs sbt. A relative path is relative to the directory of `h34s.config.mjs`; an absolute path also works. Use `/` as the separator, so the config works on every platform. The default, `'.'`, is that directory, so a config next to `build.sbt` needs no `sbtRoot`.

Set `sbtRoot` when the Nuxt app is not at the root of your sbt build. For a Nuxt app in `web/` below the sbt build, write `web/h34s.config.mjs`:

```js
import { defineConfig } from '@yuri4n/h34s-nuxt/build'

export default defineConfig({
  sbtRoot: '..',
  modules: [{ project: 'server', output: 'server/.scala' }],
})
```

For an sbt build next to the app, for example in `../scala-server`, write `sbtRoot: '../scala-server'`. The `output` paths stay relative to the application root, and the outputs must stay inside it. Point the linker of your sbt build at them, for example `(LocalRootProject / baseDirectory).value / "web" / "server" / ".scala"` for the app in `web/`. In development, the module embeds the Scala sources from both the application root and `sbtRoot` in the source maps.

Before it starts sbt or removes any output, the CLI checks that `sbtRoot` is a directory with `build.sbt` or a `project/` directory, the files that sbt looks for. Otherwise it stops with an error that names `sbtRoot`, the resolved directory and the config file. For example, a config in `web/` without `sbtRoot` gives:

```text
[h34s] sbtRoot is not set, so the sbt build is the config file's directory, /home/you/shop/web, which has no build.sbt and no project/ directory. Set sbtRoot in /home/you/shop/web/h34s.config.mjs to the directory of your sbt build, relative to that file, for example '..'.
```

The CLI also stops, with an error that names the output, when `sbtRoot` is an `output` directory or lies inside one: a production build removes the outputs, so it would remove your sbt build too.

## Add the Nuxt module and scripts

In `nuxt.config.ts`:

```ts
export default defineNuxtConfig({
  modules: ['@yuri4n/h34s-nuxt'],
})
```

The module reads the same config, maps `#h34s/models` to the generated models (see [use the models in your app](02.routes.md#use-the-models-in-your-app)), mounts the routes of each output's route manifest (`h34s-routes.json`) as lazy Nitro handlers, watches the generated output, installs the development loader/source-map integration, and registers the h34s Nitro plugin (`runtime/h34s.mjs`). The plugin gives your Scala handlers, through internal records that requests cannot change: <!-- claude 2026-10-20: changed: the models alias (ADR-0014) -->

| Record entry                                               | Used by                                                                      |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------- |
| `development` (Nitro's `import.meta.dev`)                  | Development diagnostics                                                      |
| `debug` (`runtimeConfig.h34s.debug`, read once at startup) | Debug diagnostics; see [debugging](12.debugging.md)                          |
| `runtimeConfig` (per request and at startup)               | `RuntimeConfig` / `ZRuntimeConfig`; see [configuration](05.configuration.md) |
| `storage(base)` (Nitro `useStorage`)                       | `KHubKv.mount` / `ZHubKv.mount`; see [Nitro storage](11.storage.md)          |
| `onClose` (Nitro's `close` hook)                           | `Shared` / `ZShared` release; see [lifetimes](06.lifetimes.md)               |

<!-- claude 2026-10-20: changed: the module declares false; Nuxt's debug option is not used (issue #25 comment) -->

The module also declares `runtimeConfig.h34s.debug: false`, so `NUXT_H34S_DEBUG=true` can turn on diagnostics at runtime. A value your `nuxt.config.ts` already sets wins. Nuxt's own `debug` option does not turn them on. Keep it off in production.

Remove copied versions of those hooks and the old `h34s-development` plugin when adopting the module. If you listed `runtime/development.mjs` in `nitro.plugins` yourself, remove that entry: the module registers the new plugin, and the old file only re-exports it for one release.

Add these scripts to `package.json`:

<!-- claude 2026-10-20: created: the project tour reads the block after this marker (issue #52) -->

<!-- tour: package.json -->

```json
{
  "scripts": {
    "scala:fast": "h34s-scala dev",
    "scala:watch": "h34s-scala watch",
    "scala:full": "h34s-scala build",
    "dev": "node --enable-source-maps node_modules/nuxt/bin/nuxt.mjs dev",
    "dev:scala": "pnpm run scala:fast && pnpm run dev",
    "build": "pnpm run scala:full && nuxt build"
  }
}
```

Run `pnpm dev:scala` for the first link and Nuxt startup. Keep `pnpm scala:watch` in a second terminal while editing Scala. The watcher runs sbt's continuous linking task and collects the routes again after each link; it does not start Nuxt. Wait for linking and Nitro's worker restart before requesting edited code. When the list of routes changes, Nuxt reloads its server routes without a restart.

After each link, `dev`, `build` and `watch` load the linked modules in a separate Node process, read the route and response types of each h34s handler, and write `h34s-routes.json`, one `.d.ts` per handler module and `h34s-models.d.ts`, the named models that the routes return, into the output directory. The command prints the number of routes and models. See [routes and typed `$fetch`](02.routes.md). <!-- claude 2026-10-20: changed: the models file (ADR-0014) -->

For production, `pnpm build` clears each generated output directory, runs `fullLinkJS`, verifies the configured entry files, writes the route manifests and declarations, and only then starts the Nuxt build. A linker failure, a missing entry, an output without handlers, or two handlers for the same route stops the command. The Nuxt module alone does not run a production link; keep that ordering in the application build script.

The CLI accepts `--root <directory>`, the application root (default: the current directory), and `--config <file>`, relative to that root. Configure an alternate file in Nuxt with `modules: [['@yuri4n/h34s-nuxt', { configFile: 'custom.mjs' }]]`. Keep the Nuxt integration and CLI pointed at the same application configuration. To run sbt in another directory, set [`sbtRoot`](#point-the-cli-at-your-sbt-build) instead of these flags. sbt must be available on `PATH`. <!-- claude 2026-10-20: changed: the flags' defaults, and sbtRoot for another sbt directory (ADR-0009) -->

The `./build` entry point also exports `loadConfig`, `buildScala`, `linkScala`, `watchScala`, `writeRoutes` (collect routes and write the manifests and declarations after your own link step) and `readRoutes` for custom orchestration. The `./rollup` entry point exports `scalaDevModules`, `scalaSourceMaps` and `scalaPrerenderStub` (the plugin behind `scalaPrerender: 'stub'`) for custom integrations. Ordinary Nuxt applications use the module above; they do not need to wire these helpers individually. <!-- claude 2026-10-19: changed: scalaPrerenderStub export -->

Large linked outputs make Nitro's production bundling memory-hungry. When your application prerenders a route, Nitro 2.13.1 bundles the linked Scala.js twice in one build process: once for its prerenderer and once for the server output. The repository demo, which links a Kyo and a ZIO application, sets the `scalaPrerender: 'stub'` option below and still runs `nuxt build` with `node --max-old-space-size=8192`. If your build stops with a JavaScript heap error, raise the limit the same way, try the option, or remove one of the causes in the [development guide](../../development.md#production-build). <!-- claude 2026-10-19: changed: the scalaPrerender option as a remedy -->

### Keep Scala.js out of the prerender bundle

Set the module option `scalaPrerender: 'stub'` in `nuxt.config.ts` when you prerender routes and none of them needs Scala.js: <!-- claude 2026-10-19: created: the scalaPrerender option, example first (issue #30, review F4) -->

```ts
export default defineNuxtConfig({
  modules: [['@yuri4n/h34s-nuxt', { scalaPrerender: 'stub' }]],
})
```

The option decides what Nitro's prerender bundle gets from your Scala.js outputs in a production build: <!-- claude 2026-10-19: created: the table's introduction -->

| Value                    | Prerender bundle          | Server output (`.output/server`) <!-- claude 2026-10-19: created: the table header --> |
| ------------------------ | ------------------------- | -------------------------------------------------------------------------------------- |
| `'bundle'` (the default) | The linked Scala.js       | The linked Scala.js <!-- claude 2026-10-19: created: the default -->                   |
| `'stub'`                 | One stub that answers 501 | The linked Scala.js <!-- claude 2026-10-19: created: the stub -->                      |

With `'stub'`, every import of a file in a configured output directory resolves to the stub while Nitro builds its prerenderer. Every export that your code imports from it is an h3 event handler that throws a 501 error with the status message `Scala.js is not bundled for prerendering (h34s scalaPrerender: 'stub')`. h3 treats it as a handled error, so Nitro does not log it as unhandled. The option changes nothing when no route is prerendered, in `nuxt dev`, or in the server output. The stub covers the output directories in `h34s.config.mjs`; Scala.js that your code imports from another directory is still bundled. <!-- claude 2026-10-19: created: what the stub does; the 501 is a handled h3 error (review F2) -->

For example, Nuxt Content prerenders its database dump, which runs no Scala.js code, so the demo sets `'stub'`. Keep the default when a prerendered page fetches data from a Scala.js route. While Nuxt prerenders that page, the request answers 501 instead of running your handler, and h34s prints a `[h34s]` warning that names the request by its method and path; it leaves out the query string and fragment, which can hold tokens. After prerendering, the build stops with an error that lists these requests: each one once, sorted, at most 20, and then the number of the others. The `[h34s]` warnings name every request. Without that error, a page that catches the 501, as `useFetch` does, would be saved with its error state and the build would pass. Nuxt 4 shares `useFetch` and `useAsyncData` results, failed ones too, between the pages it prerenders (`experimental.sharedPrerenderData`), so other pages that use the same data, for example through a shared layout or component, may hold the same error; check every prerendered page that renders a listed call. When Nitro stops the build itself, because a prerendered route answered with an error, h34s logs the list as an error and Nitro shows its own summary of the failed routes. With `nitro.prerender.failOnError: false` (Nuxt sets it to `true`), h34s only warns, and those pages keep their error state. <!-- claude 2026-10-19: created: when to use the stub, and the build error for a prerendered request (review F1); what the list shows, shared data, and Nitro's own failure (review F1, F3, F4); no query strings in the log (Codex review) -->

A Nitro plugin that calls Scala.js code at startup gets the stub in the prerenderer too. The stub then throws while Nitro loads the prerender bundle, before any page is prerendered, so the build stops with the stub's own message, not with the list of requests. `nuxt generate` prerenders every page that it finds by following links from `/`, so check those pages before you turn the option on. <!-- claude 2026-10-19: created: plugins and nuxt generate; a plugin stops the build before the list (review F5) -->

Any other value stops Nuxt with a `TypeError` that names the option. The option removes the second copy of the Scala.js, not every heap problem. In the demo on a 15.7 GiB cloud VM, a build with the option passed with a 4096 MiB heap limit, and prerendering took 3.6 seconds instead of 47 to 59. At Node's default limit on that VM, 2240 MiB, a build with an equivalent temporary hook still ran out of memory while it built the server output. ## Set up a project with `h34s-scala init`

**Status.** `init` is new in `@yuri4n/h34s-nuxt` `0.3.0-alpha.1`, which is not released yet. `0.2.0-alpha.1` does not have it. Until the release, set up your project by hand with the [adoption guide](02.adoption.md).

`h34s-scala init [directory]` sets up h34s once in a project. You run it without installing anything first, after the `@yuri4n` scope and its token line are in your `~/.npmrc` (see [Install the tooling](#install-the-tooling)):

```sh
pnpm dlx @yuri4n/h34s-nuxt@<version> init my-app
```

`init` finds the adoption path from the files in the directory. The directory defaults to the current one. The first row that matches wins:

| Files in the directory                                 | Path                  | What `init` writes                                                                                                                                                          |
| ------------------------------------------------------ | --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `nuxt.config.*`, or a `package.json` that lists `nuxt` | An existing Nuxt app  | The sbt build at the Nuxt root: `build.sbt`, or `h34s.sbt` next to an existing `build.sbt`. It merges the scripts and dependencies into `package.json` and adds the module. |
| `build.sbt`                                            | An existing sbt build | A new Nuxt app in `web/` with `sbtRoot: '..'`, and `h34s.sbt` next to your `build.sbt`, which `init` does not edit.                                                         |
| Nothing yet                                            | A new project         | A minimal Nuxt app, pinned to Nuxt 4.3.1, and its sbt build.                                                                                                                |
| Other files                                            | None                  | Nothing. `init` stops and asks you to run it in your Nuxt app or sbt build, or with a new directory.                                                                        |

"Nothing yet" means that the directory is missing, empty, or holds only repository files: `.git`, `.gitignore`, `.gitattributes`, `.editorconfig`, a README and a license. So you can run `init` in a fresh clone. When the parent directory has a `build.sbt`, a Nuxt app or a directory with nothing yet is the Nuxt app of that sbt build, with `sbtRoot: '..'`. So `init web` in your sbt build gives the same result as `init`, and so does `init` in `web/`. When `h34s.config.mjs` exists in the directory, in its Nuxt app or in its sbt build, `init` prints "Already set up" and changes nothing: it runs once per project.

Every path gets `h34s.config.mjs`, the sbt project `server` in `scala-server/` with one hello handler for `GET /api/hello`, `.jvmopts` and the `project/` files when they are missing, the `.npmrc` lines and the `.gitignore` entries. The dependency versions are the version of the package that runs `init`, so the npm and Maven versions match. Kyo is the default API; add `--zio` for ZIO. Add `--dry-run` to print the plan and write nothing.

`init` checks every file before it writes any. It creates missing files only and never overwrites a file. It changes an existing file only in these ways: it appends lines to `.gitignore` and `.npmrc`, merges scripts and dependencies into `package.json`, and adds `'@yuri4n/h34s-nuxt'` to `modules` in `nuxt.config`. When it cannot make that edit safely, it prints the line to add. It keeps your own `dev` and `build` scripts and prints the values to set. On a conflict, for example a file that it would create or a script of the same name with another value, it lists the conflicts, writes nothing and exits with status 1. It installs no packages and runs no sbt. It writes no token: `.npmrc` and the sbt build only name `GITHUB_PACKAGES_TOKEN` and `GITHUB_PACKAGES_USER`, and `init` prints only whether they are set. Run `h34s-scala init --help` for the options.

**What is verified.** The unit tests of `@yuri4n/h34s-nuxt` run `init` on each path from clean temporary directories, without sbt and without a package install, and the packed-package check runs it from the packed tarball. A test checks that the files `init` writes match the blocks of this guide and the [adoption guide](02.adoption.md). A project that `init` wrote has not yet been built with real sbt and the published packages; that end-to-end check is the next step of [issue #54](https://github.com/yuri4n/h34s/issues/54).

## Keep application policy in the application

The npm package owns build orchestration, development loading, source maps, and the Nitro plugin. It has no dependency on a particular effect API.

Configure your own `build.sbt` and Maven credentials. Define models and services in your application, compose their environment in an optional `AppHandler` wrapper, and configure any database resources, migrations, secrets, and deployment policy there. Declare each route in Scala with `.at(Route...)`. A one-line route file (`export { default } from '../.scala/notes-get.js'`) still works when you prefer Nuxt's file layout for a route.

Schema remains optional. Adopting the npm package does not add ZIO, Kyo, or Schema to an application's Scala dependency graph. Nix and other future build profiles should call the same CLI pipeline. Windows, Nix/NixOS, and additional deployment targets still need their own validation.
