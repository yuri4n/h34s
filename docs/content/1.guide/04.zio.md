# ZIO handlers

The ZIO API is a first-class, hand-written adapter over the Kyo core. You write ordinary ZIO programs: `for` comprehensions, `ZIO.service`, typed errors, `ZLayer` and `ZStream`. `ZHandler.define` runs them on a ZIO `Runtime` and hands the result to the core, which owns the request lifecycle, the wire format and the response.

Your application depends on `zio-h3-ext`, which brings the Kyo core with it. You never write Kyo code in a ZIO application.

**Status.** This guide describes `0.2.0-alpha.1`. The older `0.1.0-alpha.1` has a different ZIO API. The [migration guide](../2.reference/4.migration.md) maps every old call to its replacement.

## Prerequisites

- Scala 3.9.0, Scala.js 1.22.0, and JDK 25 to run sbt. The ZIO modules share the Kyo core's toolchain.
- ZIO 2.1.26. kyo-zio 1.0.0-RC7 pins this version; keep your own ZIO dependencies on it.
- `"dev.yuri4n" %%% "zio-h3-ext" % "<version>"`, plus `h3@1.15.4` and `@yuri4n/h34s-nuxt` in your Nuxt app.

Import the API with `import dev.yuri4n.exts.zioh3.*`. It re-exports the shared values (`Request`, `ResponseHead`, `SafeError`, `Secret`, ...).

## Write your first handler

<!-- claude 2026-10-20: changed: the quickstart sends its stream with Response.sendStream (ADR-0004) -->

A handler is a function from the request snapshot to a ZIO program that returns the body. This is the demo's database-free route (`examples/nuxt/scala/zio/.../TestHandler.scala`), which streams three letters:

```scala
import dev.yuri4n.exts.zioh3.{EventHandler, HandlerEnv, Request, Response, Route, Sent, ZHandler}
import zio.ZIO
import zio.stream.ZStream

import scala.scalajs.js.annotation.JSExportTopLevel

object TestHandler:
    val letters: Request => ZIO[HandlerEnv, Throwable, Sent] = _ => Response.sendStream(ZStream("a", "b", "c"))

@JSExportTopLevel("default", "test")
val handler: EventHandler = ZHandler.define(TestHandler.letters).at(Route.any("/api/test"))
```

The response body is `abc`. `Response.sendStream` writes the head, then the stream, and gives `Sent`, which is the handler's body. `.at` mounts the export at `/api/test` for every method: after `h34s-scala` links it, the Nuxt module registers the route, so you write no route file. See [routes and typed `$fetch`](02.routes.md).

## Keep handler functions small and testable

The demo keeps each handler as a plain value, so a test can call it with a fake request (`examples/nuxt/scala/zio/.../NotesHandler.scala`):

```scala
object NotesHandler:
    val list: Request => ZIO[Notes, Throwable, List[NoteView]] =
      _ => ZIO.serviceWithZIO[Notes](_.list).map(_.map(NoteView.from))

    /** The schema validates and trims the input before any database work; the handler adds no
      * validation code.
      */
    val create: Request => ZIO[HandlerEnv & Notes, Throwable, NoteView] = request =>
      for
        input <- request.body.json[CreateNote]
        note  <- ZIO.serviceWithZIO[Notes](_.create(input.text))
        _     <- Response.status(Status.Created)
      yield NoteView.from(note)

@JSExportTopLevel("default", "notes-get")
val listNotes: EventHandler = AppHandler.define(NotesHandler.list).at(Route.get("/api/notes"))

@JSExportTopLevel("default", "notes-post")
val createNote: EventHandler = AppHandler.define(NotesHandler.create).at(Route.post("/api/notes"))
```

Nuxt types `$fetch('/api/notes')` as `{ data: { id: number; text: string }[] }`: `NoteView` derives `NativeSchema`, which describes the JSON it writes.

`Notes`, `Note` (the domain note), `NoteView` (the JSON it sends), `CreateNote` (the JSON it reads) and `AppHandler` are demo code. Define your own.

## Read the request

The `Request` snapshot is the same value the Kyo core uses; see [Kyo handlers](03.kyo.md#read-the-request) for every member and for the body status codes. The ZIO signatures:

| Call                          | Type                                     |
| ----------------------------- | ---------------------------------------- |
| `request.body.json[A]`        | `IO[HttpError \| InvalidInput, A]`       |
| `request.body.json[A](limit)` | the same, with an explicit `BodyLimit`   |
| `request.body.text()`         | `IO[HttpError, String]`                  |
| `request.param(name)`         | `IO[HttpError, String]`; 400 when absent |

## Return a body

<!-- claude 2026-10-20: changed: a stream is sent with Response.sendStream, not returned (ADR-0004) -->

| Return type                                | Response                                                                                   |
| ------------------------------------------ | ------------------------------------------------------------------------------------------ |
| Any `A` with a `NativeConverter`           | 200 (or the status you set) with `{"data": <value>}`                                       |
| `Unit`                                     | 204 with no body, unless you set another status                                            |
| `Sent`, from `Response.sendStream(stream)` | The stream's strings, written as UTF-8 text as they come; see [streaming](09.streaming.md) |

A `ZStream` is not a body. To stream, end your handler with `Response.sendStream(stream)`, where the stream is a `ZStream[Any, E, String]` with `E <: Throwable`, and return its `Sent`. A handler that returns a `ZStream` does not compile. `ZHandler.sendStream` is gone; see the [migration guide](../2.reference/4.migration.md).

## Set status, headers and cookies

<!-- claude 2026-10-20: changed: Response.sendStream joins the head operations (ADR-0004) -->

`Response` has the same operations as the Kyo API, as `URIO[ZState[ResponseHead], Unit]`: `status`, `header`, `appendHeader`, `cookie`, `deleteCookie(name, path, domain, secure, onFailure)`, `redirect`, and `head`. h34s writes the head once, after your program and its finalizers finish. `Response.sendStream(stream)` is the one exception: it writes the head as it stands when it runs, then the stream, and gives `Sent`. The failure rule is the same: on failure, the status comes from the error, and only handler defaults, `OnFailure.Keep` entries and the error's headers survive.

Two ZIO details:

- `ZState` is backed by a `FiberRef`. A forked fiber works on its own copy of the head; joining it copies the child's head back into the parent (ZIO's default `FiberRef` join). Set response entries in the request fiber when you can.
- `catchAll` and other recoveries do not roll back head changes.

An invalid header name or value, cookie name, or redirect status makes the effect die, and h34s answers with a 500.

## Fail safely

| Failure                                                              | Status             | Body (default options)                               |
| -------------------------------------------------------------------- | ------------------ | ---------------------------------------------------- |
| `ZIO.fail(safeError)`                                                | `safeError.status` | `{"errors":[{"message":"..."}]}`                     |
| `ZHandler.failWith(status, msg, msgs*)`                              | `status`           | one entry per message                                |
| `InvalidInput` from a body read                                      | 422                | one entry per schema message, with `path` when known |
| Any other typed failure, a defect, interruption, or several failures | 500                | `{"errors":[{"message":"Internal server error"}]}`   |

`ZHandler.failWith` fails with `ErrorResponse(errors, status)`, as in `0.1.0-alpha.1`. `ErrorResponse` is not a `SafeError` (its `errors` field is a `NonEmptyList[String]`), so `catchSome { case e: SafeError => ... }` does not catch it; h34s approves both at the boundary. A `SafeError` or `ErrorResponse` stays approved even when sibling fibers were interrupted with it (for example in `zipPar`). Any other `Throwable` in the error channel is not approved: catching an exception and failing with it does not make it public. Map it to your own `SafeError` instead.

<!-- claude 2026-10-19: changed: a dying finalizer is logged and keeps the response, as in Kyo (issue #40); the rule covers the request scope only (review) -->

A ZIO finalizer that dies does not change the response, as in Kyo: h34s logs `h34s: a ZIO finalizer failed` with ZIO's `Cause.prettyPrint` on the server, and the client gets the value, the `Unit` response or the safe error that your program produced. Do work that must affect the response in the program, not in a finalizer. The rule applies to the request scope that h34s owns (finalizers your handler adds with `ZIO.addFinalizer` or `ZIO.acquireRelease` in its request `Scope`). A release that dies inside your own `ZIO.scoped` block, or inside a scoped layer that you provide inside the handler, fails the program under ZIO's rules and answers 500, as before. In development or debug mode, the diagnostics of a failed program show ZIO's full `Cause.prettyPrint`, with ZIO traces and Scala source lines.

## Choose the wire format

`ZHandler.define(options)` takes the same `HandlerOptions` as the Kyo core:

```scala
ZHandler.define(HandlerOptions(defaults = ResponseHead.noStore)): request =>
  ...
```

See [Kyo handlers](03.kyo.md#choose-the-wire-format) for the envelopes, defaults, body limit and `requireJsonContentType` (see [cross-site requests](03.kyo.md#cross-site-requests)).

## Compose services in your AppHandler

Write one wiring point that provides your layers. This is the demo's (`examples/nuxt/scala/zio/.../AppHandler.scala`):

```scala
object AppHandler:
    /** Every response is `Cache-Control: no-store`; bodies use the default `{ "data": ... }` envelope. */
    private val options = HandlerOptions(defaults = ResponseHead.noStore)

    /** One Skunk pool for all requests: built on first use, released when Nitro closes. */
    private val database = ZShared.layer(SessionPool.layer)

    def define[B: ZResponseBody](program: Request => ZIO[HandlerEnv & Notes, Throwable, B]): EventHandler =
      ZHandler.define(options): request =>
          database.provide(program(request).provideSomeLayer[HandlerEnv & SessionPool](NotesLive.layer))
```

<!-- claude 2026-10-20: changed: HandlerEnv carries the transport of Response.sendStream (ADR-0006) -->

`HandlerEnv` is `ZState[ResponseHead] & Scope & HandlerTransport`: what h34s supplies to every ZIO handler. The `Scope` is the request scope. It stays open while `Response.sendStream` sends a stream. `HandlerTransport` is the native response that `Response.sendStream` writes; h34s provides it, and `ZHandler.test` provides it in a test, so you never build it.

Use ordinary `provide`, `provideSomeLayer` and `ZLayer` composition. A `ZLayer` value is rebuilt each time you provide it. For a resource that all requests share, such as a pool, wrap the layer in `ZShared`; see [lifetimes](06.lifetimes.md).

`ZHandler.define` runs on `Runtime.default` unless a `given Runtime[Any]` is in scope. You do not need to create one.

## Type aliases

| Alias                                                                                 | Meaning                                           |
| ------------------------------------------------------------------------------------- | ------------------------------------------------- |
| `HandlerEnv`                                                                          | `ZState[ResponseHead] & Scope & HandlerTransport` |
| `ZHandler[R, E, A]`                                                                   | `ZIO[HandlerEnv & R, E, A]`                       |
| `Handler[E, A]`, `TaskHandler[A]`, `URHandler[R, A]`, `UHandler[A]`, `RHandler[R, A]` | The usual ZIO shapes over `HandlerEnv`            |
| `TaskStream[A]`, `RStream[R, A]`, `URStream[R, A]`                                    | `ZStream` shapes                                  |
